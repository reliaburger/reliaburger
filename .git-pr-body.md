## What this does

`relish upgrade start v0.2.0` rolls a live cluster onto a new binary:

- **Node swap**: verify dual Ed25519 signatures (compiled-in release key set + operator key from `node.toml`), stage into a versioned binary store, atomic symlink swap, `execv` in place — same PID, workload child processes untouched.
- **Workload adoption**: instance records (pid + start-time fingerprint) let the new binary adopt still-running workloads instead of restarting them; ProcessGrill logs moved to files so output survives the exec (pipes would SIGPIPE workloads). RunC adoption via `runc state` + pid liveness.
- **Automatic rollback**: a crash-looping new version burns a boot-attempt budget recorded in an on-disk marker, then startup recovery reverts the symlink and execs the previous binary. Nodes remember reverted upgrade ids and refuse re-delivery (closes a revert/re-send livelock); `upgrade resume` retries under a fresh id.
- **Rolling orchestration**: leader walks workers (batches of `--parallel`) → council one at a time (quorum-gated) → leadership transfer (`trigger().elect()` on an upgraded member) → former leader last. State lives in Raft (`DesiredState.active_upgrade`), so a leader change mid-run is a resume, not a restart.
- **CLI**: `relish upgrade check / start / plan / status / rollback / resume` (network flow via release metadata + Pickle blob distribution; air-gapped via `--binary` + `.sig`), plus `relish dev keygen / sign-binary`.
- **Retention GC**: newest `retain_versions` binaries kept, rollback targets protected.
