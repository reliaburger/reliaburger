Reliaburger · design goal

Scrutiny, not popularity

Why we ask you to trust an orchestrator for what anyone can check, not for how many people run it.

Miko Pawlikowski · November 2026 · arrow keys to move, N for notes

Open with the question: how did you decide your last piece of infrastructure was safe to run? For most of us the honest answer is "lots of people use it". This talk is about why that stopped working in 2026, and what Reliaburger does instead. Keep it under ten minutes.

The old rule

"Given enough eyeballs, all bugs are shallow"

  • Linus's Law, as Eric Raymond put it: popular code is safe code, because someone would have noticed.
  • Heartbleed: in OpenSSL for over two years before anyone said so.
  • Log4Shell: in every Log4j from 2.0-beta9 to 2.14.1.
  • xz: caught by one engineer curious about slow ssh logins, in "an unpaid hobby project".

Sources 1–5

Lots of users is not the same as lots of reviewers. Heartbleed: shipped in OpenSSL 1.0.1 (March 2012), found and disclosed in April 2014. Log4Shell: CISA's guidance gives the affected range 2.0-beta9 to 2.14.1. xz: Andres Freund noticed ssh logins using too much CPU and valgrind errors; Russ Cox's timeline quotes Lasse Collin calling xz "an unpaid hobby project". Don't overstate it: the rule worked often enough to feel true.

2026

Finding bugs got cheap

948distinct Linux kernel bugs with working root exploits, in one OpenAI run, for about $1.2M
6,202high- or critical-severity bugs Anthropic estimates across 1,000+ open-source projects
~2,000kernel vulnerabilities found in release 7.2, up from ~500 at 6.9

Sources 6–9

Be exact. OpenAI's post, "A thousand fewer paths to root" (November 2026): 2,308 candidate findings, 1,724 reproduced, 1,169 working local privilege-escalation exploits, 948 distinct bugs after grouping by root cause, $1,213,430 in API credits. These are local privilege escalations, so an attacker needs an account first, and nobody outside OpenAI has verified the count. It's not 948 CVEs: within ten days about 100 were patched or had staging patches. Anthropic's Glasswing update (22 May 2026): 23,019 findings in total, an estimated 6,202 high or critical, 530 disclosed, 75 patched so far. The kernel numbers are Greg Kroah-Hartman's, via Linux Pro Magazine; they count vulnerabilities found, which says how hard people look, not how many bugs were added.

So what changed

Popular code is searched hardest, by everyone

  • The same models work for both sides. Popularity now mostly means you're first in the queue.
  • What counts is how quickly a fix reaches every machine you run.
  • On Kubernetes that's many queues: the project's own feed lists 95 CVEs since 2017, and etcd, containerd, runc, Helm and Argo CD each keep their own.
  • One add-on, ingress-nginx, scored 9.8 in March 2025, and Wiz found it in about 43% of cloud environments.

Sources 10–11

The Kubernetes count is ours: we downloaded the official JSON feed on 10 November 2026 and counted 95 entries, 13 published in 2026. The feed covers only issues the Kubernetes Security Response Committee announces; it includes subprojects such as ingress-nginx (22 entries mention it) but not etcd, containerd, runc, Helm or Argo CD. IngressNightmare is CVE-2025-1974 and three siblings, CVSS 9.8.

Reliaburger's answer

Make it cheap to check, and quick to fix

  • Open, and readable by any model. Apache 2.0; every release relish carries its exact source, and relish agent source lets your agent read it.
  • One binary, one advisory stream. Ingress, registry, metrics, logs, PKI, consensus and GitOps are compiled into bun.
  • One patch upgrades everything. relish upgrade start rolls a signed binary across the cluster, with automatic rollback.
  • Less code, in Rust. One code base instead of a platform plus a dozen add-ons.

Source 12

This is the design goal in the whitepaper's section 2. The point isn't "we have no bugs". It's that we make bugs cheap to find and a fix quick to ship. Rust matters here more than the line count: Google measured about a thousand times lower memory-safety vulnerability density in Android's Rust than in its C and C++.

Sources 13–15

Methods. make loc runs scripts/loc.sh, which counts tracked files with wc -l and treats a file's #[cfg(test)] tail and its test modules as test code (317,973 test lines). Crates: cargo tree -e normal --target x86_64-unknown-linux-gnu, unique name and version pairs, minus Reliaburger itself; Cargo.lock lists 741 packages across every platform and the dev dependencies. Releases: tags v0.1.0 (29 September) to v0.2.7 (7 November 2026). The planted bug is the agent gym's planted-logs-since scenario in 0.2.7's exit test, run with a read-only token.

Honest limits

What this doesn't buy you yet

  • 274k lines isn't small, and we haven't measured Kubernetes the same way, so there's no ratio to quote.
  • Machines check the code daily (fuzzing, mutation tests, a dependency audit), but LLM reviews still happen when someone starts one.
  • One binary is one target: a bug in bun is on every node.
  • The host patches separately: kernel, glibc, runc, nftables.
  • Before 1.0 a format change means a fresh cluster, and a person starts every upgrade.
Say these out loud; the audience will think of them anyway. The next step is a scheduled LLM review of the whole code base, published as it runs, which turns "can be scrutinised" into "is scrutinised". It isn't built, and there's no issue for it yet. The crates bring their own advisories too: on 26 October 2026 RustSec published 13 against one compression crate, and 0.2.3 shipped with them under a dated, reviewed exception.
