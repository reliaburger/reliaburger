Install it #

INSTALL sh
curl -fsSL https://reliaburger.com/install.sh | sh

One line installs relish, then builds a three-node cluster in Linux VMs on your laptop, running real containers. It checks every download against a pinned digest or the release’s signing key.

You’ll need macOS, or Linux with QEMU and KVM, plus about 8 GiB of free memory and 15 GiB of disk. No Rust, no checkout.

One node, CLI only, cleanup · Read the bootstrap script · Release notes ↗

Try it in five minutes #

Install, then put the cluster through its paces: a real Kubernetes app, a network fault, a killed replica and a lost node. Same prerequisites as the install line.

Show the commands every step, with what to look for 
  1. curl -fsSL https://reliaburger.com/install.sh | sh

    Installs relish, then builds a three-node cluster in Linux VMs on your laptop. It checks every download against a pinned digest, and it’s the only step that takes minutes.

  2. relish apply -f https://reliaburger.com/demo/podinfo.yaml

    A real Kubernetes app: podinfo’s frontend, backend and Redis cache, plus a small load generator so there’s always traffic. Relish converts the YAML as it applies it and tells you what it had to change.

  3. relish status
relish council status

    Give it half a minute. Three frontend replicas, one on each node, named frontend-0, -1 and -2. The scheduler spread them and numbered them across the cluster, not you. status opens with a line on the council, the Raft group that holds the cluster’s state; council status asks every node for its own view of it: its role, term and log position, with the leader and quorum on top.

  4. open http://podinfo.localhost:18080

    Or paste the address into a browser. It comes in through the built-in ingress; reload and the hostname changes as each replica answers.

  5. curl -fsSL https://reliaburger.com/demo/burger.tar.gz | tar xz
relish build burger/burger.toml
relish images
relish apply burger/burger.toml
curl http://burger.localhost:18080/order

    Now an app of your own: a small Go service and its Dockerfile. A node builds it with Buildah, straight into the cluster’s own registry, signed, for both linux/amd64 and linux/arm64: images lists burger:v1 once, with its platforms. Each order names the podinfo backend that cooked it, found by its service name.

  6. Development preview (0.2.0 / PR #266): queue 1,000 small and 64 larger jobs beside the burger service.

    relish --output json batch submit burger/jobs.toml
relish batch watch 1
relish batch results 2 --failed --limit 20
relish manual batch

    Use the returned manifest ID instead of 1 and the small profile’s child ID instead of 2. CPU and memory requests decide what fits; chunk size decides how much is queued. Watch rates, backlog and duration distributions, then inspect a bounded failure page. The executable tour includes this step with --jobs and checks that the app still serves orders. This step needs development binaries; the 0.1.4 recording above predates it. A short demo does not qualify 100 million jobs/day.

  7. relish path frontend --to redis

    Walk the path from a frontend to Redis, hop by hop: DNS, the virtual IP, the eBPF service map in the kernel, the firewall, any active faults, then a real TCP connect from inside the frontend. On Kubernetes you’d piece that together from five tools and a debug pod.

  8. relish metrics frontend

    podinfo’s own Prometheus metrics, from every replica. Each node read the manifest’s prometheus.io annotations and scrapes its own replicas. There’s no Prometheus to install.

  9. relish fault delay redis 300ms --from frontend --duration 2m --acknowledge

    Now make Redis slow, but only for the frontends. Every packet they send it waits 300 ms; anything else calling Redis doesn’t notice. It lifts itself after two minutes. No chaos tooling to install either.

  10. relish path frontend --to redis --count 3

    The same path, now DEGRADED. It names the fault, shows the delay it found on the frontend’s network interface, and every connect takes 300 ms.

  11. relish metrics frontend --name http_request_duration_seconds

    Wait twenty seconds, then look at latency per replica. It was under a millisecond; now it’s in the hundreds, and a cache read through the ingress takes almost a second.

  12. relish dashboard

    The same thing as live charts in your browser: CPU, memory in MiB, requests per second and latency in milliseconds, one line per replica. Ctrl-C closes it; the cluster keeps running.

  13. relish fault kill frontend --count 1 --acknowledge
relish status

    Kill a frontend. Run status again a few seconds later and it’s back, with a restart counted: the node agent restarts what should be running.

  14. relish local stop node-3
relish inspect frontend

    Now lose a whole machine. About a minute later there are three running frontends again, spread over the two nodes that are left: each keeps the one it had, and one of them starts a replacement under the lost one’s name. Nobody had to notice first. inspect asks every node, lists each instance, running or stopped, with the node it’s on, and names the node that didn’t answer.

  15. relish wtf

    One screen on what’s wrong and what to do about it. Here: a council member is missing, and one more failure would lose quorum. It also checks that every node runs the same build. It’s what you’d run first in a real incident.

Finished? Remove the cluster, then Relish itself:

relish local destroy --yes
relish uninstall

Or build it from source #

Hacking on Reliaburger itself? Start with a local process. No container runtime required.

You’ll need Rust and the build tools for your platform. This example runs hello under the built-in ProcessGrill runtime; it doesn’t create an isolated container or a multi-node cluster.

For real OCI containers, use runc on Linux. On macOS, the managed laptop quickstart uses Linux VMs. Direct Apple Container is deferred beyond 0.1.5.

Build requirements & runtime setup ↗
LOCAL DEVELOPMENT sh
# Terminal 1 · build and start the agent
git clone https://github.com/reliaburger/reliaburger
cd reliaburger
cargo build --bins
target/debug/bun --runtime process

# Terminal 2 · from the same checkout
target/debug/relish apply \
  examples/phase-1/proc-first-run.toml
target/debug/relish status
target/debug/relish
Web dashboard: http://127.0.0.1:9117/
