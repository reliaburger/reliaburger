# V02: sustained TLS, storage, restart and upgrade qualification

25 September 2026. The plan for V02 in
[the v0.1.0 remaining work](2026-09-22-v0.1.0-remaining-work.md): the release
candidate has to survive a day or two of repeated failures and recover every
time, and every failure along the way has to be explained before we accept it.
It covers the open items C03, C05, C11, C14, C44, C47 and item 263.

## Decisions

The maintainer took three decisions on the research draft.

- **D1: a short-lifetime knob.** We add `[security] leaf_lifetime_override_secs`
  (development safety class only, 600 s ≤ value ≤ the default). The soak uses
  3600 s, so node and cluster ingress leaves renew about every 30 minutes
  instead of twice a year. The harness only sets it when the running bun
  accepts the key (see G1 below), so it also runs against today's candidate.
- **D2: a private soak build.** For upgrade walks we build bun at the
  candidate commit with version `0.1.0-soak.1` (semver below 0.1.0), sign it
  locally with the production release key through
  `relish dev sign-binary --key`, and never publish it. The record carries its
  hash; it is deleted after the soak. Upgrade with
  `relish upgrade start --binary bun-v0.1.0-soak.1`, roll back with
  `relish upgrade rollback v0.1.0`. Downgrading to it needs
  `--allow-downgrade` since #198.

  In a cluster `upgrade start --binary` is a network upgrade: the nodes fetch
  the build from node 1's registry, so each wants a second signature from the
  operator key in `[upgrades] external_signing_key`. The first dry runs never
  set one and every walk was refused. The harness now plays the operator. It
  makes a throwaway Ed25519 key with `openssl genpkey` (kept in the evidence
  as `config/operator.key`, so `--resume` reuses it), puts its public key in
  every node.toml (a recorded deviation), and writes a copy of the soak
  build's envelope to `upgrade/bun-v0.1.0-soak.1.sig` with that key's
  signature added. The release signature is copied as it is: the harness
  never needs the release key. `relish dev sign-binary` couldn't do this,
  since it always signs with the release key, so there is now
  `relish dev countersign-binary --external-key KEY BINARY`, which does the
  same for operators. The harness uses openssl rather than that command, so
  it works with whatever relish the candidate ships; both give the same bytes
  (Ed25519 signatures are deterministic).
- **D3: two tiers, a fast loop and an 8-hour final run.** On 25 September
  the maintainer chose one 12-hour lane A run on the final candidate. That
  run (candidate 2e93b67, `staging-v0.1.0-36173986955-1`, 25–26 September;
  [record](../qualification/2026-09-26-v02-soak-12h.md): FAIL, no data lost)
  showed the feedback loop was far too slow, so on 26 September lane A
  became two tiers:
  - **Fast tier** (`--tier fast`): the compressed schedule for 90 minutes.
    Cycles 0–3 carry every fault kind (both bun kills, the deploy kill, a
    power-off, all seven chaos kinds, and an upgrade walk with each mid-walk
    fault) and every special, and the harness always finishes them. Run it
    after each round of fixes. It catches what shows up in the first hour; in
    the 12-hour run the log ordering, `relish test` from the host and the
    upgrade refusal all did.
  - **Final tier** (`--tier final`): the full schedule for 8 hours, once per
    final candidate. It catches slow accumulation. The 12-hour run found bun
    RSS growth at 4.8 hours, a registry 503 at 5.4 and a memory-high alert at
    6.2; a 4-hour run would have missed all three. The specials scale with
    the length, so 8 hours gets graceful whole-cluster restarts at hours 4
    and 8, quorum losses at 3 and 7 and every VM off at 6, and the harness
    always completes one cycle per hour so none of them is lost to overrun.
    Two chaos kinds per slot reach all seven in the four chaos slots an
    8-hour run with upgrade walks has (the 12-hour run, at one a slot, never
    ran `drop` or `dns`). Expect about 15 identity rotations per instance,
    15 node renewals per node and 4 upgrade round trips.

  The record names its tier. A fast run can say "fast tier: clean" but never
  claims acceptance; only a clean final-tier run (8 hours, full schedule,
  digest checked) says the V02 gate passes.

## What we know

- **Certificates.** Node leaves last a year, hard-coded in
  `src/sesame/ca.rs` (`node_cert_params`), and renew at their midpoint
  (`src/sesame/renewal_worker.rs`: 1 s check, 5 s retry). Cluster-issued
  ingress leaves last 90 days (`src/bin/bun.rs`). Workload identity lasts an
  hour, rotates at 30 minutes and gets 4 hours' grace when the council is
  away (`src/sesame/identity.rs`). The root CA lasts 10 years, intermediates 5,
  and `bound_leaf_validity` clamps leaves. TLS connections live an hour and
  drain 30 s before (`src/sesame/connection.rs`). An operator
  `[ingress] tls_cert/tls_key` pair reloads within a second, and an invalid
  replacement keeps the last good pair while it stays valid
  (`src/wrapper/tls.rs`, `tests/suite/ingress_file_reload.rs`).
- **Observing them.** `GET /v1/diagnostics` gives each node's leaf
  `not_after`, `serial` and `rotation_state` (valid, renewing, retrying,
  expired, stopped). Workload certificates are `cert.pem`, `key.pem`, `ca.pem`,
  `bundle.pem` and `token` under `/run/reliaburger/identity` in every app
  container; every app gets one, there is no opt-in.
- **Storage knobs.** `[logs] export_path`, `export_interval_secs` (≥ 1),
  `max_storage_mb`, `retention_days`; `[metrics] export_path`,
  `max_storage_mb`; `[storage.snapshots] interval_secs`, `retain`,
  `upload_url`. The disk-pressure tick runs every 300 s and exports before it
  prunes (`src/bun/disk_pressure.rs`). Exports land as
  `<dest>/<node>/<sha256>-<file>.parquet` beside a checkpoint and its lock
  (`src/ketchup/export.rs`); snapshots upload as
  `<dest>/<ns>/<app>/<volume>/<name>.tar.gz`.
- **Volumes aren't placement-aware.** A managed volume lives on one node, and
  an app rescheduled elsewhere starts on an empty one. The soak pins its
  volume apps with node labels.
- **Upgrades.** Release builds ignore `upgrades.release_keys_override` and the
  `.version` sidecar; the version is `CARGO_PKG_VERSION`. An upgrade to the
  running version is a no-op, so a same-version upgrade with different bytes
  silently "succeeds" (`src/upgrade/orchestrator.rs`). The air-gapped
  `--binary` path takes the version from the file name and expects
  `PATH.sig`; rollback needs an explicit version; nothing refuses a downgrade.
  The upgrade registry defaults to `{api host}:5050`, which the quickstart's
  host forward can't serve (G3), so the harness runs upgrades from inside
  node 1 with `--registry <node 1 address>:5050`.
- **The quickstart.** Bun runs as `reliaburger.service` (Restart=on-failure,
  KillMode=process). `/etc/reliaburger/node.toml` is every default section
  pretty-printed, mode 0600. VMs are `rb-<id12>-N`; limactl is
  `$RELIABURGER_HOME/tools/lima-2.1.0/bin/limactl` with
  `LIMA_HOME=$RELIABURGER_HOME/lima`. Node N's API is forwarded to
  `api_port + N - 1`; only node 1 forwards ingress (guest port 80) and the
  registry. The fault policy is `development` with `inject_workload_faults`
  and `alter_node_state` only. `relish local stop` is graceful and needs
  `--yes` for node 1 or a quorum node.
- **Tooling quirks.** `relish status` fails with 503 while any node is down.
  `relish wtf` exits 1 on critical findings and 2 on warnings or unknowns.
  `relish exec` reaches the first running instance on the node whose API it
  talks to. `relish test --filter` takes kebab-case groups (`volumes`,
  `image-registry`, `workload-identity`, `ingress`, `deployments`). The CLI
  ignores the certificate host name on loopback endpoints; curl needs
  `--connect-to <node>:9117:127.0.0.1:<port>`.

## 1. What we sustain

**TLS (C14).** Per 24 hours: at least 250 workload identity rotations, with
`not_after` always more than ten minutes away; at least 24 connection
retirements per long-lived stream with at most one reconnect each; the
operator ingress pair rotated every 15 minutes with 45-minute leaves from a
soak CA, and every fourth offer an invalid pair (torn, or expired), at least 96
reloads in all; node and cluster ingress leaves on the 3600 s override, at
least 48 renewals per node.

**Storage (C03, C11, C47, volumes, Pickle).**

- A volume writer (busybox, managed volume, pinned to node 2) appends a
  sequence about ten times a second, syncs, and logs `ACK n`. The file must
  hold 1..N with no gaps and N at least the highest ACK. That file check
  (`writer-gap`, `writer-regression`) is the data-loss authority. The light
  check also reads the `ACK` and `INCR` lines through `relish logs`; a number
  that falls there is a `writer-log-order` or `redis-log-order` failure,
  which says the log view returned lines out of order, not that data was
  lost.
- Redis (pinned to node 3, `appendonly yes`, `appendfsync always`) takes an
  `INCR` every second from a client; the counter never goes backwards.
- A log spammer writes about 200 lines a second.
- Every node exports logs and metrics to
  `file:///var/lib/reliaburger/soak-export/{logs,metrics}` every 60 s with
  `max_storage_mb = 8`, and snapshots volumes every 900 s, retaining 4,
  uploaded beside them. Every Parquet file that leaves the source must be at
  the destination, byte-identical; retained archives must stay readable.
- Every six hours an offline `relish logs-export --source` contends for the
  exporter's checkpoint lock from another process (C03), and
  `relish logs-search` over the destination still works.
- Hourly, a small unique image goes into Pickle; every heavy check re-fetches
  every image pushed so far and checks its SHA-256.

**Restarts, hourly.** In order: SIGKILL a follower's bun
(`kill -9 $(systemctl show -p MainPID --value reliaburger.service)`, not
`systemctl kill`); SIGKILL the leader's bun; a rolling deploy with a SIGKILL
0–20 s later on a node receiving a replacement (C05); a hard VM power-off
(`limactl stop --force`) held 60–180 s, then `relish local start`, every fourth
on node 1; a chaos fault (`relish fault kill|delay|partition|pause|drop|dns`,
or the `dead_worker_node_has_workloads_rescheduled` scenario). Kill and pause
meet the replica-minimum rail, so both aim at the three-replica frontend, one
replica at a time: `kill --count 1`, and a pause of one running instance
(`--instance`). The network faults (delay, drop, partition, dns) meet no
replica rail. Every 12 hours
a graceful whole-cluster stop and start. At 20 and 40 hours, quorum loss (two
nodes off for five minutes), which must recover without `council recover`. At
36 hours every VM off at once.

**Upgrades (C44, item 263).** Every two hours v0.1.0 → 0.1.0-soak.1 → v0.1.0;
every other walk with a fault mid-walk (power off a follower, or SIGKILL the
leader's bun). At least 12 walks in 24 hours. Other faults pause during upgrade
slots.

## 2. The harness

`scripts/release/qualify-sustained.sh` drives the run;
`scripts/release/sustained_check.py` (Python standard library only) turns
evidence into findings, keeps the running state and renders the record;
`scripts/release/test_sustained_check.py` tests it. The workloads are
`scripts/release/sustained/soak-workloads.toml`.

```sh
scripts/release/qualify-sustained.sh \
    --base-url https://github.com/reliaburger/reliaburger/releases/download/TAG \
    --qualified-digest SHA256_OF_CANDIDATE_JSON \
    --soak-bun /path/to/bun-v0.1.0-soak.1 \
    --tier final --record docs/qualification/2026-09-DD-sustained-v02.md
```

`--tier fast` is the 90-minute compressed run and `--tier final` the 8-hour
full one (D3); an explicit `--duration` or `--schedule` overrides the tier,
and without `--tier` the run is a custom one that says nothing about the gate.
`--keep` leaves
the cluster; `--home DIR` adopts a home an earlier `--keep` left; `--resume
--evidence DIR` continues an interrupted run and records the gap as a pause of
the soak clock. The whole run sits under `caffeinate -dimsu` on macOS.

**Setup.** `qualify-staged-install.sh --keep` builds the cluster from the
staged candidate in an isolated home on ports 29117–29119, 28080 and 25050, so
it never touches the real `~/.reliaburger` (the run fails if that or
`~/.local/bin/relish` changes). The harness then:

1. makes a soak CA with `openssl ca` and installs a 45-minute ingress pair on
   every node;
2. probes whether bun accepts `leaf_lifetime_override_secs`: it runs the
   installed bun against a copy of node.toml with the key and a half-set
   ingress pair, which fails validation right after parsing, so bun exits
   before starting anything. "unknown field" means no; the ingress error
   means yes;
3. edits each node.toml (backed up as `node.toml.pre-soak`), recording every
   change as a deviation: the storage knobs, `provision_isolated_workloads` in
   `[testing] allowed_operations`, the operator ingress pair, the
   `soak-volume` node labels, with `--soak-bun` the operator's
   `[upgrades] external_signing_key` (D2) and, when supported, the leaf
   lifetime;
4. applies the edits one node at a time by SIGKILLing bun, so systemd restarts
   it on the new file, and waits for that node's readiness and a healthy
   council before the next;
5. applies `examples/kubernetes/podinfo.yaml` and the soak workloads, waits
   for them, then waits for two consecutive clean checks and records each
   node's leak inventory as the baseline.

**Checks.** Every 30 s a light check: podinfo through the ingress forward and
the writer's and the client's latest log lines. Every 5 minutes a heavy check:
`relish wtf`, `relish nodes`, `relish status`, `/v1/diagnostics` per node, and
one guest report per node with the leak inventory (runc containers, veths,
`/run/netns`, cgroups under `reliaburger/`, `/sys/fs/bpf` pins, listening
ports, network-lease allocations, bun's fd count, RSS, restart count and new
panics in the journal, storage sizes), the served ingress and API
certificates, the exporter source and destination and the snapshot archives.
It also reads a workload certificate on each node through `relish exec`, runs
a contiguity check over the writer's file, and re-verifies the registry.

**Schedule.** Six slots per cycle (an hour, or ten minutes compressed): :00
follower kill, :10 leader kill, :20 deploy and kill, :30 power-off, :40 chaos,
:50 settle and snapshot, followed by the registry push, the offline export
when due, the hourly catalogue pulse
(`relish test --profile full-runc --filter volumes,image-registry,workload-identity,ingress,deployments`)
and the specials. Every second cycle the upgrade walk replaces :20–:40; without
`--soak-bun` those cycles run the normal slots and the record says the walks
were skipped. Each chaos slot runs the next two of the seven chaos kinds. The
compressed schedule runs the pulse on cycle 0, one of each special on cycles
1–3, a chaos slot after every upgrade walk and a fault in every walk, so
cycles 0–3 cover everything; the run always finishes those four cycles, and a
full run always finishes one cycle per hour of its length, even when faults
overrun their slots.

**Settling.** After each fault the harness opens a fault window, in which
outages count as progress rather than failures, and then waits for two
consecutive clean checks: no critical `wtf` finding, `replicas` OK, one leader
and three live voters, podinfo answering and no leak beyond the baseline plus
current instances. Deadlines: 5 minutes after a SIGKILL or chaos fault,
8 minutes after a power-off, 10 minutes for upgrade walks and specials.

**Evidence** lives in `/var/tmp/reliaburger-v02.XXXXXX/`: `events.jsonl` (ts,
phase, target, command, exit, duration, verdict, settle time), `snapshots/`
(raw evidence plus `verdict.json` per check), `failures/<n>/` (summary, the
snapshot, 15 minutes of every node's journal, status, `wtf`, diagnostics and
the checker state), `metadata.json` and `state.json`. The record gives the
candidate identity, soak-build hash, host, Lima and guest versions, config
deviations, timeline, runs and settle times per fault class, renewal and
rotation counts against what the elapsed time requires, data progress, fd,
RSS and disk trends, and a failure table with class, cause and action columns
for triage to fill in.

The Actions lane is `.github/workflows/v02-loops.yml` on
`push: branches: [v02-loops]`, reusing the nextest archive pattern from
`ci.yml` and `sudo -E` for privileged Linux. Loop results report rule-of-three
bounds: no failures in n runs puts the rate below 3/n at 95% confidence.

## 4. Pass and fail

A single occurrence of any of these fails the gate until it is root-caused and
fixed or dispositioned:

- **Data:** a writer gap or regression, the Redis counter going backwards (as
  far as the log view shows it; a `*-log-order` failure also fails the gate,
  as a log ordering bug until triage shows otherwise), a
  registry digest missing or changed, an exported file lost or unreadable, a
  retained snapshot missing.
- **Certificates:** a served or diagnosed `not_after` within 5 minutes (10 for
  workload certificates); `rotation_state` expired or stopped, or retrying for
  more than 10 minutes; the old serial still served more than 5 s after a new
  pair lands (the reload polls every second; the rest is measurement through
  limactl); an invalid operator pair served; fewer renewals or rotations than
  the elapsed time requires.
- **Recovery:** no leader for more than 30 s with at most one node down;
  quorum not back within 120 s of the second node returning; a fault that
  doesn't settle by its deadline; a node not alive, or not a voter, outside a
  fault window.
- **Leaks after settling:** runc containers, network namespaces or network-lease
  allocations without an instance; veths or cgroups beyond the baseline plus
  new instances; new bpf pins or listening ports; bun's hourly minimum fd count
  rising for six hours; RSS 25% above its first sample after an hour's warm-up.
- **`wtf`:** a critical finding for more than 5 minutes, or a warning for more
  than 10, counted from the last settle and outside fault windows.
- **Upgrades:** a walk or rollback taking more than 10 minutes, or ending on
  the wrong version.
- **Bun:** any panic, and any systemd restart that no harness kill explains.
- **Loops:** any failure.

Allowed inside fault windows only: ingress errors and latency while a node is
lost, and one reconnect of a long-lived client.

**Triage.** Each failure gets a `failures/<n>/` bundle and a record row
(symptom, first seen, class Product, Harness, Environment or Tool, cause,
action). A failure that passes on re-run goes into Known flakes the same day. A
product fix means a failing regression test first, then the fix, then a new
candidate (V03 re-stage) and a restart of the lane. Environment failures pause
the soak clock (recorded). The harness bundles a repeated failure of the same
check and target once per half hour; the verdicts keep every occurrence.

**Acceptance.** Lane A's fast tier is clean, then one final-tier run (D3)
on the final candidate completes 8 consecutive hours with no unexplained
failure. A product fix found during the final run means a new candidate, a
fresh fast-tier run and then a fresh final-tier run. Every loop lane is green
and every failure row is closed.

## 5. Order

Lanes: A the quickstart (3 × 2 GiB, 6 vCPU), B `reliaburger-test` (8 GiB,
4 vCPU), C `rb-v02-crash` (about 6 GiB, 2–4 vCPU), D Actions. Build the lane B
and C test binaries before lane A's timed window.

**The CI lane.** `.github/workflows/soak.yml` runs lane A's harness on a
hosted `ubuntu-24.04` runner (x86_64, 4 vCPUs, 16 GiB, KVM opened to the
runner user by a udev rule, QEMU installed by the job), so a staged candidate
gets a soak without tying up a laptop. It's a smoke lane for future releases,
not a substitute for lane A: hosted jobs stop at 6 hours, so it covers the
compressed schedule and full-schedule runs of about four hours, never the
12-hour acceptance window; it has no soak build, so upgrade walks are
skipped (signing one in CI is a documented follow-up in
[releasing.md](../releasing.md#soaking-a-candidate-in-ci)); and it exercises
Lima's QEMU driver on Linux rather than VZ on macOS.

1. Spike: manual upgrade and rollback from inside node 1 with
   `--registry <node 1 address>:5050`; the Lima guest clock after a power-off;
   the registry push recipe.
2. G1, then rebuild and restage.
3. Build and sign the soak bun.
4. The harness (G5, this plan's section 2).
5. The power-cut fixtures, then `v02-loops.yml`.
6. A two-hour dry run on the compressed schedule.
7. Start the loop lanes; lane A goes round the fast tier after each round of
   fixes, then runs the final tier once on the final candidate (D3); the C05
   sweep.
8. The final record, `docs/progress.md` ticks (C03, C05, C11, C14, C44, C47,
   item 263) and the flake register.

## 6. What building the harness already found

The dry runs on the staged candidate (`staging-v0.1.0-36078958881-1`) hit
product bugs before the first cycle finished. They are candidates for V02
failure rows, not harness workarounds, except where noted.

1. **A restarted bun crash-loops for good when an instance is waiting for its
   address release.** After a rescheduling, a node keeps its old instance
   "stopped; its addresses are released once every node confirms the
   withdrawal", with its runtime intent in phase `retiring`. Any restart of
   bun in that state (a graceful `systemctl restart`, a SIGKILL, even a VM
   reboot) exits at once with `container default__frontend-0 state
   unavailable: runtime retirement requires recovery before adoption`
   (`src/grill/runc/owned.rs`), and systemd restarts it every two seconds
   forever. Two wedged nodes lose the council. In the 40-minute dry run the
   first follower SIGKILL wedged node 2 and the leader SIGKILL wedged node 1.
   The exit path also panics inside Tokio (`A Tokio 1.x context was found,
   but it is being shutdown`). The harness applies its node.toml changes with
   a SIGKILL rather than a graceful restart, which is the path the soak
   exercises hourly anyway, but that doesn't avoid this bug.
2. **The official Redis image can't write a managed volume.** With
   `args = ["redis-server", "--appendonly", "yes", ...]` the image's
   entrypoint drops to the redis user and Redis stops with `Can't open or
   create append-only dir appendonlydir: Permission denied`. The volume root
   belongs to the container's root. The soak runs `redis-server` as `command`
   instead, so the entrypoint never drops privileges.
3. **A failing app is redeployed every two seconds without limit.** The same
   Redis app reached generation `g170` within eight minutes, each attempt
   logging `runtime did not expose a process identity for durable replacement
   adoption` or `deploy refused: target ... is already being changed`.
4. **The staged-install tour's `relish path frontend --to redis` failed once
   in three bootstraps** with `0 of 0 backends healthy` just after every app
   reported running. The harness notes a tour failure after the install and
   carries on.
5. **Node labels added to node.toml don't always reach the cluster.** In one
   of four setups node 2 restarted with `soak-volume = "writer"` in
   `[node.labels]`, but `relish nodes` kept showing `"labels": {}` and the
   scheduler logged `no eligible nodes` for the pinned writer for ten minutes.
   The harness now waits for the labels, records a failure row and restarts
   the node once more.
6. **A node brought back from a hard power-off never becomes ready.** Its
   `discovery:startup-cleanup` stays degraded with `cannot retire artifacts
   for default__soak-redis-0 yet: other nodes have not yet confirmed the
   endpoint's withdrawal`, `relish local start` gives up after 45 s, and the
   orchestrator logged `startup cleanup still owns runtime allocations` 511
   times in 25 minutes while the pinned Redis stayed down.
7. **Workload identity never reached the followers' containers.** In the
   fourth dry run `soak-identity` on nodes 2 and 3 had an empty
   `/run/reliaburger/identity` for the whole 76 minutes; node 1's instance got
   its certificate within a minute.
8. **The writer's volume came back empty after the whole-cluster graceful
   stop and start.** The writer had acknowledged 36318 synced writes; after
   the restart it resumed from nothing and the file ended at 1877 lines. The
   managed volume is a loop-mounted image; the likely cause, still to
   confirm, is that it isn't mounted again at boot.
9. **An exported Parquet file was empty at the destination.** After the same
   stop and start, node 1's `…-logs_000066.parquet` in the `file://`
   destination had the SHA-256 of empty input in three consecutive checks,
   while the checkpoint counts it as exported, so pruning the source would
   lose it (C03).
10. **Acknowledged writes were lost in a hard power-off.** In the 10-minute
    validation run, powering off node 2 (`limactl stop --force`) took the
    writer back from `ACK 7305` to `ACK 7269`: 36 writes it had synced and
    acknowledged were gone. This needs triage between the product (the
    loop-mounted volume image) and the environment (Lima's `vz` disk cache
    on a forced stop); C47 covers the same question on a disposable VM.
11. Minor: the quickstart writes the host's macOS temporary directory into
   every guest's `[process_workloads] script_dir`.
12. **Every upgrade walk was refused** for want of the operator's signature.
    A harness gap, not a product bug; fixed as described under D2.
13. **The replica-minimum rail refused every pause.** The harness paused
    `soak-spammer` (one replica), and the rail rightly said no; but it counted
    any pause as freezing every replica, so a pause of one frontend instance
    out of three was refused too. The rail now counts an `--instance` pause
    as one replica, and the harness pauses one frontend instance. Candidates
    before this fix still fail `chaos-pause`.
14. Minor: `relish uninstall` on Linux ended with "this relish (…/bin/relish
    (deleted)) wasn't installed by install.sh", because it asked where it was
    running from after deleting itself. It now asks first.
15. Minor: the record called the writer's and Redis's "went backwards"
    findings as if they were data loss; they come from the log view. They
    are now `writer-log-order` and `redis-log-order` (see section 1), still
    failures.
16. **A completed walk's rollback was refused** in the first fast-tier run
    (candidate eced11c): the harness rolled back the moment every node
    reported the soak build, but the leader marks the run Completed on a
    later tick, so the rollback got "already in progress" and the cluster
    stayed on the soak build. The harness now waits (up to 120 s) for
    `relish upgrade status` to show no run in progress before rolling back;
    a paused run needs no wait, because rollback replaces it.
17. **A power cut made the log view end below an earlier tail** (fast tier on
    eced11c, after every VM was powered off): the writer's and Redis's last
    few hundred stdout lines hadn't reached disk, as with any log, while the
    writer's file and Redis's counter lost nothing. The harness now tells the
    checker when it cuts a node's power; the next tail may then end below an
    earlier one once (recorded as info, and the log-order baseline restarts
    there). Lines going backwards within one tail still fail, and the highest
    acknowledged value the writer's file must hold never goes down.
