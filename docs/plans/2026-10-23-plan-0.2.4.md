# 0.2.4: Extension points

0.2.4 gives teams ways to bend Reliaburger without forking it, before real fleets arrive with the appliance OS in 0.3.0. It covers four things:

- policies stored in the council: CEL deny and warn, then fill-only defaults, on the one apply path that `relish apply` and GitOps share;
- three escape hatches: sidecars, stop hooks and gated runtime knobs;
- an exec secret provider;
- templates that expand to ordinary apps, plus a contract for running your own controller.

There are no webhooks, no CRDs and no dynamic libraries.

The design and its reasons are in the [extension points research](2026-10-19-research-extension-points.md), agreed on 19 October 2026. Every issue body is self-contained: why, what, tests to write first and done-when. This plan only fixes the order and the shared rules.

## The train

- **Branch:** `release-0-2-4`, cut from the tip of `release-0-2-3` on 23 October 2026, while 0.2.2 was being qualified and 0.2.3 was still open.
- **Gate PR:** a draft into `release-0-2-3`, so its diff shows only 0.2.4. It retargets to `main` once 0.2.3 has merged. It carries a `Fixes #N` line for every issue here, because closing keywords only fire on merge into `main`.
- **Each issue is one PR into `release-0-2-4`.** Whenever `release-0-2-3` moves, it's merged into the train, never rebased.
- **Version:** the crate stays at whatever `release-0-2-3` has until 0.2.3 ships.
- **Compatibility:**
  - The train opens at 53/70, the same as 0.2.3, and doesn't bump when it opens.
  - 0.2.3 has 54/71 earmarked for its own first wire or state change.
  - The first 0.2.4 PR that changes the wire or durable state bumps `CURRENT` once, to 55/72. That's almost certainly #1117, because policies are a new Raft kind.
  - Later ones add a line under the 0.2.4 heading in `src/compatibility.rs`.
  - When the 0.3.0 train catches up, it goes above 0.2.4.

### The `cel` crate decision (#1117, 23 October 2026)

#1117 checked `cel` 0.15 before building on it. Its repository runs the CEL
conformance suite, and our own table of the features policies use (field
access, `has()`, `in`, string and list functions, macros, int comparisons)
passed on the first run. It has no cost model or step limit; the parser only
caps nesting at 96. So we kept CEL, didn't need the fixed predicate language,
and bound evaluation ourselves: every `match` and `deny` is capped at 1,024
bytes when it's committed, over one app's spec. The crate's `chrono` feature
is off, since policies see no clock.

The Wasm spike ([#1127](https://github.com/reliaburger/reliaburger/issues/1127)) stays gated in Later, as the research says.

Waves use the machine like every train: one agent per row, each with its own target directory. No more than three build agents run at once, because the laptop's disk is the limit, and `df` is checked before each launch. None of this train measures throughput, so it can run beside 0.2.3's bench waves only when those aren't measuring. It never runs during a release soak.
