# Remaining work for 0.1.0 — 22 September 2026

The release is not ready. C34 remains the correctness blocker; V01–V04 are
acceptance gates. The installer, static website, release signing workflow,
server-side withdrawal ledger/receipts and consumer ownership store exist.
They do not substitute for end-to-end cleanup and release qualification.

These are planning estimates of focused engineering effort, including writing
regressions and investigating ordinary failures. One day means roughly eight
hours. They are not measured completion times or promises. CI queueing, soak
duration, access to clean machines and review/merge add elapsed time. New faults
found during crash or upgrade testing can extend the ranges substantially.

| Remaining work | Difficulty | Estimated effort | Completion evidence |
| --- | --- | --- | --- |
| C34: consumer publication, recovery, confirmed withdrawal and receipt retry | High | 2–4 days | Persist exact original service/ingress exposures before publication; recover before publishing; drain captured requests positively; replay receipts safely; bounded safe compaction. |
| C34: producer release and stale execution-report fencing | High | 1–2 days | Reuse host ports/addresses only after committed consumer proof; delayed reports cannot republish retired executions; permanent decommission discharges only the fenced identity. |
| C34: actual Bun death, cancellation and host reboot | High | 1–3 days | Real OCI init/preparation/start/adopt/retire/retry interruptions preserve ownership; reboot uses positive boot identity and runtime absence evidence. |
| C34: select durable runtime/kernel/discovery paths in production | Medium–high | 0.5–1 day | Production selection uses qualified ownership/recovery paths; actual death and upgrade/rollback checks pass. |
| V01: complete live three-node acceptance | Medium–high | 0.5–1 day | Full supported catalogue, chaos, diagnostics, storage and cleanup matrix on independent Runc nodes. |
| V02: sustained TLS/storage/restart/upgrade qualification | High | 0.5–1 day, plus 24–48 hours running | Retained final-source/candidate evidence through sustained failures and recovery; investigate any failures before acceptance. |
| V03: exact signed release candidate | Medium | 2–4 hours, plus review/merge and CI | Main contains the reviewed code/workflow; build once, stage through HTTPS, install and verify those exact bytes; promotion does not rebuild. |
| V04: repeated cold laptop installation matrix | Medium–high | 0.5–1.5 days, plus host availability | Clean supported hosts, including Intel macOS, reach a working cluster in under five minutes; retain timing and failure/cleanup evidence. |

Total working estimate: roughly **6–14 engineering days**, plus external waits
and soak time. Several qualification runs can overlap, but the consumer/producer
correctness work must precede final release acceptance. Re-estimate once the
complete remote cleanup loop passes its first crash/recovery tests.

V05 dependency review is complete for the current lockfile with dated exceptions.
Optional refactors and explicitly deferred features are not new release blockers.
Fresh pre-release clusters, foreground-only native processes and the managed
Linux VM for macOS containers remain the agreed release scope.
