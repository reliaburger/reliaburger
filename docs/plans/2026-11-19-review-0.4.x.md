# Review: the 0.4.x releases, before we start them

19 November 2026. Checked against the 0.3.0 train (`release-1-3-0` at
`2b93e529a`, formats 60/76) and `main` at `40ae8478b`. The maintainer agreed
the split and settled all but two of its questions the same day; what was
decided, and what's still open, is at the end. No code moves with this plan.
The roadmap, the feature list and the GitHub milestones changed with it.

The maintainer asked four questions while 0.3.0 and 0.3.1 gate:

1. Does the 0.4.x plan still make sense?
2. Has anything we've shipped since changed what we should build?
3. Is the split into 0.4.0 to 0.4.5 still right?
4. What else would make Reliaburger a real alternative to Kubernetes?

## The short version

1. **The direction holds; the documents don't.** "Take a node down without
   taking your database down" is still the right headline for the user we
   named: three people, four machines, one unreplicated PostgreSQL. But the
   [migration plan](2026-10-09-plan-container-migration.md) (9 October) and the
   [VM research](2026-10-19-research-vm-runtime.md) (19 October) each describe
   a code base that has moved on in about ten places.
2. **0.3.0 already ships half of 0.4.1.** The appliance has a leader-driven
   rolling OS update that cordons, waits, reboots and checks health, one node
   at a time. What it lacks is a real drain to wait for. Sidecars, stop hooks,
   proposals, leases, policies and the job model all change what a drain and a
   move must do, and the VM plan's headline field, `runtime = "vm"`, now
   collides with a table that 0.2.4 shipped.
3. **The split should change.** 0.4.0 carries the cheapest, most-missed feature
   (cordon and drain) in the same release as the riskiest (CRIU checkpoints),
   plus four unrelated features. 0.4.2 lost its headline to 0.2.7 and 0.2.8.
   We propose six releases with one headline each. Moves that keep memory come
   after the VM runtime and are done by VMs; CRIU goes to Later (decided, 19
   November).
4. **The gaps that turn evaluators away aren't on the 0.4.x list.** They are:
   no upgrade without a fresh cluster, a volume app that waits for ever when its
   node dies, no health check a database can pass, no way for outside traffic to
   find a healthy node on bare metal, and no export to the tools a team already
   runs. Two of them deserve a 0.4.x headline of their own.

## 1. Does the plan still make sense?

### Container moves (0.4.0, 0.4.1): yes, reordered

The user and the pitch are right, and 0.3.0 makes them more right: we now ship
an OS that updates itself every week, so every appliance cluster reboots every
node every week.

What's changed is where the value sits. Look at what the named user actually
runs. Their PostgreSQL has a volume, so a **cold move** serves it: stop, carry
the volume, start, a pause of seconds. Their replicated apps need only
**drain**. Checkpoint moves help the memory-only Redis and the long
computation, which is a smaller group, and they carry nearly all of the risk:
sixteen of the plan's twenty-one spikes, CRIU's refusal list, and Incus's
warning that only "very basic containers" move reliably.

So drain and cold moves should ship first, alone. The plan already allows for
this (decision 10: a failed spike never holds back the modes that work). We'd
make it the schedule, not the fallback.

**Decided, 19 November:** container checkpoint moves go to Later. With the VM
runtime this early, a VM snapshot is the way an app keeps its memory across a
move, and CRIU returns only if the VM spike V4 fails. What that costs is under
"Decided" at the end.

One outside fact has moved. The plan says Kubernetes doesn't move a running
container between nodes. That's still true, but Kubernetes now has an alpha
pod-level checkpoint and restore
([KEP-5823](https://www.kubernetes.dev/resources/keps/5823/), milestone 1.37),
with cross-node restore named as a follow-up. The plan was right not to lean on
the contrast. The comparison page should say "alpha, same node" when we get
there.

### "Let the AI SRE help" (0.4.2): no, it has no headline left

The roadmap describes 0.4.2 as "human-approved mutations through proposals,
agent tokens labelled in audit, a merged incident timeline". 0.2.8 shipped all
three. What's left in the
[milestone](https://github.com/reliaburger/reliaburger/milestone/18):

| Issue | What's left | State |
|---|---|---|
| [#1082](https://github.com/reliaburger/reliaburger/issues/1082) | A per-token read rate limit and a session id in audit | Tokens shipped; these two not started |
| [#1084](https://github.com/reliaburger/reliaburger/issues/1084) | A server-side `/v1/timeline`, GitOps and log-pattern sources | The client-side merge shipped (`src/relish/agent/timeline.rs`) |
| [#1087](https://github.com/reliaburger/reliaburger/issues/1087) | Log patterns in Ketchup | Not started |
| [#1089](https://github.com/reliaburger/reliaburger/issues/1089) | Alertmanager-compatible webhooks | Not started; only generic, Slack and PagerDuty payloads exist (`src/mayo/webhook.rs`) |
| [#1091](https://github.com/reliaburger/reliaburger/issues/1091) | OpenTelemetry export | Not started |
| [#1092](https://github.com/reliaburger/reliaburger/issues/1092) | A remote MCP endpoint in `bun` | Not started; `rmcp` is built with the stdio transport only |
| [#1837](https://github.com/reliaburger/reliaburger/issues/1837) | Local models, phase 2 | Phase 1 shipped |

Read that list again without the word "agent". OTLP export, Alertmanager
webhooks, a timeline API: it's about connecting Reliaburger to what a team
already runs. That's a good release. It needs a new name, and it wants
[#1773](https://github.com/reliaburger/reliaburger/issues/1773) (custom alert
rules) beside it, since Alertmanager-shaped webhooks for five fixed rules is
half a feature.

One loose end: [#1093](https://github.com/reliaburger/reliaburger/issues/1093)
closed with its part 1 (read-only diagnosis) passed and a comment that "the
proposals half stays for 0.4.2". No open issue tracks that second exit test.

### The VM runtime (0.4.3 to 0.4.5): yes for apps, a question for disks

The case for `VmGrill` hasn't weakened. The code it leans on is still there
(`Grill`, `MixedGrill`, `RuntimeKind`, `NodeCapabilities`), and one of its five
spikes is partly answered already: the
[V04 cold-install record](../qualification/2026-11-12-v04-cold-installs-linux.md)
ran nested KVM under Lima's VZ driver on an M5, with QEMU as the inner VMM.
Cloud Hypervisor itself hasn't been tried there.

Three things deserve a second look:

- **Who it's for.** The 0.3.0 exit hardware is a Dell Wyse 3040: 2 GB of RAM,
  about 1.0 to 1.3 GB left for workloads, and VT-x that our own research marks
  "unverified". The quickstart's nodes have 2 GiB each. The VM runtime's
  natural home is a bigger machine than either of the two places people will
  meet Reliaburger. That's fine, but the exit test needs a named machine, and
  the manual needs to say what the Wyse can't do.
- **VMs may be the better way to keep memory.** A VM snapshot has no refusal
  list, works on arm64 with pre-copy, and covers everything in the guest.
  Since 0.2.4 an app instance can be several runc containers sharing one
  network namespace (see below), which is exactly the shape CRIU finds hard.
  Cloud Hypervisor 54 also promises live migration across at least its two
  previous releases
  ([Phoronix, 14 October 2026](https://phoronix.com/news/Cloud-Hypervisor-54)),
  which is the mixed-version rollout case the move plan's spike S20 worries
  about. This is why moves that keep memory come after the VM runtime, and
  why VMs carry them.
- **"Bring your own disk" (0.4.5) is a different product.** Cloud images, UEFI,
  ISOs and a serial console compete with Proxmox, not with Kubernetes. Home
  labs would love it, and they're who we say we're for today. But it does
  nothing for the gaps in section 4, and the 19 October decision to keep it in
  0.4.x was made before 0.2.7 and 0.2.8 pulled the agent work forward and
  before an outside evaluation told us where the product is thin.

## 2. What we've shipped that changes the plans

Each item names the plan it affects and what should change. Paths are in the
0.3.0 train.

### The move plan

Items 5, 10 and 11 concern CRIU. With container checkpoints in Later they
matter only if CRIU comes back, and they stay here so that whoever reopens it
starts from today's code.

1. **A rolling OS update already exists.** The plan says that activating an A/B
   slot "means rebooting the node and restarting everything on it", and makes
   the rollout 0.4.1 work. In 0.3.0, `src/os/rollout.rs` runs it from the
   leader with its state in Raft: workers first, then council members while
   quorum can spare one, then the leader; each node goes Pending, Draining,
   Updating, Done; it pauses on a refusal, a failed boot or a 45-minute
   timeout; and `relish os upgrade|status|resume|abort` drive it. What "drain"
   means there is thin: wait up to five minutes (`DRAIN_TIMEOUT`) for the
   scheduler to re-place apps without a managed volume, then reboot anyway.
   Volume apps go down with the node and come back with it. So 0.4.x doesn't
   build the rollout. It gives the rollout a real drain to call.
2. **There are three cordons, and none is the operator's.** The bun upgrade
   cordon (`apply_upgrade_cordon`) and the OS rollout cordon
   (`apply_os_rollout_cordon`) are both derived from Raft state in
   `src/meat/filter.rs`; Smoker's `node-drain` fault is a third, node-local
   mechanism. `relish status` and `relish nodes` show only the first
   (`src/bun/api/summary.rs:551`). The plan's "generalising today's upgrade
   cordon" now means one cordon record with a reason (operator, upgrade, OS
   rollout, fault) that all four writers use and every view reads.
3. **The rollout and the plan disagree about host-path apps.** The plan's
   decision 8 says they block a drain. The rollout's `undrained()` counts them
   as movable, so the scheduler re-places them away from their data. One of the
   two is wrong today.
4. **A node shutdown skips stop hooks.** 0.2.4 gave apps `pre_stop`,
   `stop_signal` and `stop_grace`. A deploy honours them. A Bun shutdown, which
   is what an OS reboot is, sends SIGTERM, waits five seconds
   (`SHUTDOWN_GRACE_SECS`) and kills. Every volume app on an appliance takes
   that path once a week. A drain must retire instances through the path that
   runs the hooks, and the availability budget for a singleton has to include
   its `stop_grace`.
5. **An instance is no longer one container.** Sidecars (0.2.4) are separate
   runc containers that join the app's network namespace, with their own
   cgroups (`src/grill/oci.rs`). Init containers are extra containers too. The
   plan's spike S-A checkpoints "a container built by today's `RuncGrill`".
   It must now include an app with a sidecar, or checkpoint moves must refuse
   sidecar apps by name.
6. **The job paragraphs don't match the job model.** The plan says array tasks
   "with attempts left requeue". Since 0.2.0, a task interrupted mid-run
   becomes `Unknown` and is never replayed unless the job sets
   `replay_unknown`; only bulk submissions keep at-least-once replay. Reusable
   executors (0.2.0, 0.2.3) run tasks inside a shared container that idles out
   after a second. Two consequences. A drain has to stop new grants to the
   node and wait for held chunks, and it looks as though a Raft cordon doesn't
   stop grants today (grants follow `sync_targets`; we haven't traced this end
   to end). And the plan's step "a running single-attempt task moves with its
   run id" would checkpoint an executor shared with other tasks. We'd drop
   that step: a drain waits for hooks up to their deadline, and names what it
   waited for.
7. **Drains and moves should be proposals.** 0.2.8's proposals model "these
   apps go from this state to that one", with nine kinds, none for a node.
   Leases lock an app or a namespace, never a node. Guardrail policies already
   see a `nodes` field. So 0.4.0 adds `drain`, `uncordon` and `move` as
   proposal kinds and a node lease target, and "an agent proposes the drain, a
   person approves it" comes almost free. The new `[app.x.move]` table must
   also join the policy field list, which a test compares with `AppSpec`.
8. **Moves need to show up where 0.2.8 put everything else.** `relish
   timeline` has no event kind for a node, a cordon, a move or an OS rollout
   (`src/bun/events.rs`); rollout progress is only printed. `relish agent
   explain` has no rule for a move or a drain decision
   (`src/bun/decisions.rs`). The plan's "move phases appear on the dashboard
   timeline" should become: an event kind, a decision rule, and a line in the
   one-screen status.
9. **Half the logs-and-metrics step is done.** The plan says Mayo and Ketchup
   both find an app's data through its current placement. Ketchup now fans out
   to every live member (`src/ketchup/query.rs`). Only Mayo's single-app query
   still needs the change.
10. **Everything runs Ubuntu 26.04 and Linux 7.0.** The plan speaks of a 24.04
    guest and of building our own CRIU if the archive has none. Ubuntu 26.04
    carries
    [criu 4.2 in universe](https://packages.ubuntu.com/source/resolute/criu),
    which meets the plan's floor. The spikes must run on 7.0, which already
    cost us an eBPF verifier fix. A test holds the guest's and the appliance's
    package lists together (`scripts/release/test_guest_images.py`), so CRIU
    joins both or neither. And our soak guests are still 24.04 with a 6.8
    kernel, so a move in the soak wouldn't test the kernel we ship.
11. **The appliance has swap.** It enables zram. The plan's decision 5 keeps
    plaintext dumps in "no-swap memory". zram is compressed RAM, so nothing
    reaches a disk, but the staging area still has to be locked or the
    decision reworded. On a Wyse with 1 GB spare, a dump that must fit in
    memory on both nodes limits checkpoint moves to small apps. Say so in the
    admission refusal.
12. **There's a transfer path to reuse.** No node-to-node volume transfer
    exists, but Pickle's peer blob pull already streams large objects between
    nodes with incremental hashing (`src/pickle/pull.rs`). Appliance volumes
    are Btrfs, so the plan's snapshot-and-send path is the common case there,
    not the exotic one.
13. **Leader-coordinated rollouts belong with drain.**
    [#1776](https://github.com/reliaburger/reliaburger/issues/1776) (one
    cluster-wide surge and unavailable budget in Raft) sits in 0.4.1. The
    drain planner's first property test is "never drops an app below its
    availability budget", which needs exactly that budget. It should move to
    0.4.0.
14. **The crate split lands first.** The
    [split plan](2026-11-08-plan-crate-split.md) runs "right after 0.3.0
    merges" and moves the configuration into its own crate. Starting 0.4.0's
    trains before it means every PR conflicts with it.
15. **The power-cut harness is the move-recovery harness.** The
    [endurance work](2026-11-18-plan-power-cut-endurance.md) cuts power to
    nodes thousands of times and checks invariants after each. The plan's
    "source-off" test wants the same machinery. Reuse it; don't write a second.

### The VM research

16. **`runtime = "vm"` can't be added as written.** Decision 1 chose the field
    `runtime` on apps, to mirror jobs. Since 0.2.4, `[app.x.runtime]` is the
    table of gated capabilities, sysctls and devices (`AppSpec.runtime`,
    `src/config/app.rs:132`), and the node's `[runtime]` section holds their
    allowlists. One of them has to move (decided below: the table is renamed).
17. **"Works as it does for runc" now covers more.** The research's validation
    section predates sidecars (which need a shared network namespace), stop
    hooks, runtime knobs (which only rootful runc applies), exec secret
    providers, `run_as_user`, ordinals and the `metrics` scrape spec. Each
    needs a line: supported in a VM, or refused with a reason. The `Grill`
    trait has also grown about a dozen capability methods a `VmGrill` must
    answer.
18. **The guest kernel isn't a by-product.** The research expects it "out of
    0.3.0's weekly OS build". That build ships Ubuntu's stock
    `linux-image-generic`. A small guest kernel is its own artefact with its
    own build, signature and CVE stream.
19. **The appliance has room, with limits.** The `/usr` slot is fixed at
    1,100 MB and the spike measured 320 to 350 MB used, so a VMM and a guest
    kernel fit. Nobody has measured it with them in.
20. **The Apple runtime is still off, and untested in CI.** The VM plan folds
    its return ([#367](https://github.com/reliaburger/reliaburger/issues/367))
    into the VM release. Since 0.2.8 the macOS CI job builds only `relish`
    ([#1741](https://github.com/reliaburger/reliaburger/issues/1741)), and
    hosted Apple runners can't nest virtualisation. It needs the self-hosted
    runner first, and it shouldn't gate the Linux VM runtime.

### What's wrong with the current one

### What we'd do instead

One headline and one exit test each, as the roadmap asks. Trains that touch
different subsystems can run side by side on the two machines.

| Release | Headline | What's in it | Exit test |

Why this order:

- **0.4.0 is useful to every cluster on the day it ships**, including every
  appliance cluster 0.3.0 creates, and it needs no spike beyond S12 (fencing).
- **0.4.1 and 0.4.2 are independent of moves** (Wrapper, Mayo and Ketchup, not
  the scheduler), so they can ride a second train while 0.4.0 gates.
- **0.4.1's failover address is S11's first half.** A cluster address that one
  node owns and announces by ARP, with an ownership generation in Raft, is the
  mechanism live moves need for a workload. Building it for the ingress first
  gives 0.5.0's go or no-go spike something real to stand on.
- **0.4.3 reuses 0.4.0's volume transfer.** A standby is a cold move's
  pre-sync that never does the final cut. On Btrfs, which is every appliance
  volume, it's an incremental send on a timer.
- **The spikes run early and cost little.** V1, V2 and V4 for VMs are a week
  each and can start now. V4 matters most: it decides whether 0.4.5 exists as
  written, or whether CRIU has to come back.

The cost is milestone churn, and renaming keeps it small. The VM milestones
keep their issues and take new numbers (0.4.3 becomes 0.4.4, 0.4.4 becomes
0.4.5). The old 0.4.5 milestone becomes 0.4.3, "When a node dies", once its six
issues have moved to Later. About twenty issues change milestone, and the
roadmap entry is rewritten. The Apple runtime's two (#367, #1741) stay with
the VM release until the maintainer decides where they go.

## 4. What would make it a real alternative to Kubernetes

We went through the
[competitor review](../research/2026-10-15-competitor-review.md), the
comparison pages, `docs/features.toml`, the manual and the code, and asked what
a team evaluating us would hit. Of the review's seven recommendations from
October, none has fully shipped: ACME, application backups, Compose import,
preview environments and telemetry export haven't started, and the safety
contract and deployment visibility are partly there.

Ranked by how often we think each ends an evaluation. The ranking is our
judgement; the gaps are facts, with their sources.

1. **You can't upgrade.** Nearly every release needs a fresh cluster, and
   in-place upgrades have worked twice (0.2.2 to 0.2.3, 0.2.6 to 0.2.7). That's
   the rule before 1.0 and it's the right rule. It's also the first thing an
   evaluator reads. Two things would help without breaking the rule. First, a
   **logical export and import**: `relish` writes a cluster's apps, jobs,
   policies, namespaces and secrets as files, and a fresh cluster on the new
   version applies them. It isn't a migration and needs no compatibility code.
   Second, a **written plan for 1.0**. The
   [milestone](https://github.com/reliaburger/reliaburger/milestone/32) holds
   one issue. Which formats freeze, and after which release?
   **Decided, 19 November:** the export and import go in, since they're cheap
   and get people across a format bump for now. The 1.0 plan waits; the
   maintainer isn't yet sure what it should look like.
2. **A volume app whose node dies waits for ever.** It moves only when you
   decommission the node, and then it starts on an empty volume
   (`docs/manual/11_images-and-volumes.md`). Snapshots upload to an object
   store, but no command restores one onto another node. For the user with the
   unreplicated PostgreSQL this is the whole question, and 0.4.0 only answers
   the planned half. This is the proposed 0.4.3.
3. **A database can't pass a health check.** Health checks are HTTP or HTTPS
   only (`HealthProtocol`, `src/config/app.rs:314`). Redis and PostgreSQL
   speak neither. It's small, and it's embarrassing next to a Redis demo.
   Proposed for 0.4.1.
4. **On bare metal, nothing brings traffic to a healthy node.** Every ingress
   node binds 80 and 443 and the manual says to put an L4 load balancer in
   front. The 0.3.0 user has three thin clients and no load balancer. With
   ACME, this is the proposed 0.4.1. Services are also TCP only, and the
   ingress HTTP only: UDP and plain TCP ingress matter to home labs (DNS, game
   servers, WireGuard) and can follow.
5. **It doesn't talk to the tools people have.** No OTLP, no Prometheus
   endpoint on `bun`, no PromQL or remote-write, no Alertmanager shape, five
   fixed alert rules. The proposed 0.4.2 covers most of it. PromQL stays the
   big one ([#364](https://github.com/reliaburger/reliaburger/issues/364)); a
   remote-write exporter is the cheap way to make an existing Grafana work.
6. **No way in from Compose.** Our audience today is home labs and small
   teams. More of them have a `compose.yaml` than a Helm chart. The review
   recommended a strict Compose import in October; it's absent. It's a few
   days' work beside the Kubernetes importer and probably the best on-ramp we
   could build.
7. **No stable API, no OpenAPI, no SDK, no Terraform provider, no deploy
   action.** The Python client and the specification are parked in 0.9.0. A
   generated OpenAPI document and a GitHub Action that runs `relish apply` are
   cheap and visible. Stability itself is a 1.0 question (item 1).
8. **No login for people.** Tokens with three roles, and no OIDC. A team of
   three doesn't care. A team of thirty stops here. **Decided, 19 November:**
   plan it in. We propose 0.4.2, because signing in through the identity
   provider a team already has is that release's headline applied to people.
9. **Three nodes is all we've qualified.** The
   [hollow-node record](../qualification/2026-10-28-hollow-nodes.md) found
   the leader refusing report connections at 500 nodes, and
   `MAX_REPORT_CONNECTIONS` is still 16
   ([#1411](https://github.com/reliaburger/reliaburger/issues/1411)). Nobody
   needs 1,000 nodes from us. A soaked, published 25 or 50 would change how
   the three reads.
10. **The developer loop.** No port-forward, no interactive exec (0.4.1), no
    preview environments
    ([#636](https://github.com/reliaburger/reliaburger/issues/636)), no local
    service development
    ([#637](https://github.com/reliaburger/reliaburger/issues/637)).
11. **Trust signals.** No SBOM, no adopters list, no governance note, and the
    outside evaluation that drove 0.2.5 isn't in the repository. The
    agent-against-Kubernetes comparison
    ([#1679](https://github.com/reliaburger/reliaburger/issues/1679)) is the
    one piece of evidence only we can publish.
12. **Where it runs.** Raspberry Pi has a plan
    ([#1994](https://github.com/reliaburger/reliaburger/pull/1994)); Secure
    Boot must be off; there's no cloud install path beyond a cloud-init
    snippet, and many people's first try is a cloud VM. **Decided, 19
    November:** the Raspberry Pi lands in a 0.3.x release, not Later. Nearly
    everyone has one, and we want people to play with Reliaburger.

### Where each one lands

With the three decisions of 19 November, the split takes six of the twelve
whole and five in part. One, trust signals, has no release.

| # | Gap | Lands in | Left without a release |
|---|---|---|---|
| 1 | Upgrades | 0.4.0: the logical export and import (decided) | The 1.0 plan, deliberately |
| 2 | A dead node's volume app | 0.4.3 | |
| 3 | Health checks for databases | 0.4.1 | |
| 4 | Traffic to a healthy node | 0.4.1 (ACME and the failover address) | UDP services, and TCP or UDP ingress |
| 5 | Existing tools | 0.4.2 (OTLP, Alertmanager webhooks, custom alert rules) | A Prometheus endpoint on `bun` and remote-write; PromQL stays in Later (#364) |
| 6 | Compose import | 0.4.1 (decided) | |
| 7 | API and ecosystem | The OpenAPI document and deploy action ride 0.4.1 or 0.4.2 (decided); stability waits for the 1.0 plan | The Python client stays in 0.9.0; the Terraform provider has no home |
| 8 | Login for people (OIDC) | 0.4.2 (decided to plan it; the slot is our proposal) | |
| 9 | Scale past three nodes | 0.4.0: #1411 and a 25-node soak (proposed in section 3) | #1412 and #1413 stay in Later |

| 11 | Trust signals | Nowhere; #1679 sits in Later | All of it |
| 12 | Where it runs | Raspberry Pi in a 0.3.x release (decided), by its own plan (#1994) | Secure Boot and a cloud install path |

Three notes on the decided ones:

- **The export has to exist on the cluster you're leaving.** Shipping it in
  0.4.0 means the first crossing it helps is 0.4.0 to 0.4.1. If the export
  half (read-only, no format change) rode a 0.3.x patch, it would cover the
  crossing into 0.4.0 as well, which is the one every appliance cluster will
  face first. Worth asking the sessions that own 0.3.x.
- **OIDC is the biggest item in 0.4.2.** It needs its own dated plan: the
  browser and device flows for `relish` and the dashboard, mapping an
  identity provider's groups to the three roles and to namespace scopes, and
  what the audit log records. Tokens stay for agents and CI.
- **The Pi plan estimates six to nine engineer-weeks** and starts with a
  one-week hardware spike, so it wants a 0.3.x release of its own after
  0.3.1, not a seat in the patch. Its four open decisions are in #1994.

For the rest, without a seventh headline: the Prometheus endpoint and
remote-write belong in 0.4.2, and port-forward in 0.4.1 beside interactive
exec. Trust signals (11) aren't features. They're documentation and
publishing work that can ride any train.

What we'd keep refusing: CRDs and operators, a CNI, CSI and network storage.
They're what makes Kubernetes heavy, and the
[extension-points research](2026-10-19-research-extension-points.md) already
chose lighter answers. The pitch isn't "everything Kubernetes does". It's that
a small team gets the outcomes (deploys, TLS, a database that survives, nodes
that patch themselves, an agent that can operate it safely) from one binary,
and can check our claims.

## Found along the way

For the sessions on 0.3.0 and 0.3.1. Not part of this plan's decisions.

- Bun's shutdown path doesn't run `pre_stop` or wait `stop_grace` (item 4
  above). Every weekly OS update takes it.
- `relish status` and `relish nodes` don't show OS-rollout cordons (item 2).
- The OS rollout re-places host-path apps away from their data (item 3).
- Task-array grants may ignore both cordons (item 6; not traced end to end).
- `docs/website/compare/kubernetes.md:161` says "No fuzzing yet"; there are
  nine nightly targets.
- `SECURITY.md:20` says a cluster takes a fix "with `relish upgrade`", which
  holds only when the formats haven't moved.
- `docs/README.md` says it describes 0.2.8, and `docs/features.toml` still
  marks 0.3.0's headline as planned. Both may be waiting for the tag.
- `main`'s roadmap still says 1.0.0 is "expected in January 2027"; the train
  already replaces it with "no target dates".

## Decisions

### Decided

By the maintainer, on 19 November 2026:

- **The split.** The six releases in section 3.
- **"When a node dies"** is something we'll promise: a standby volume with a
  stated data-loss window, as asynchronous copies only. Synchronous
  replication stays a non-goal.
- **"Bring your own disk"** leaves 0.4.x until someone asks, which reverses
  decision 4 of 19 October.
- **The `runtime` name.** 0.2.4's knob table is renamed (say, to
  `[app.x.privileges]`, since it holds capabilities, sysctls and devices), so
  that `runtime = "vm"` on an app matches jobs. It costs a format bump we'd
  take anyway. The new name is settled in the VM release's plan.
- **Job tasks don't move.** The move plan's "a running single-attempt task
  moves by checkpoint" step is dropped: a drain waits for hooks and stops new
  grants.
- **Small on-ramps.** Compose import rides 0.4.1. The generated OpenAPI
  document and the deploy action ride 0.4.1 or 0.4.2, whichever train has
  room.
- The logical export and import go in, and the 1.0 plan waits (section 4,
  item 1).
- OIDC login gets planned (item 8).
- The Raspberry Pi lands in a 0.3.x release (item 12).
- **Container checkpoints (CRIU) go to Later.** 0.4.5 is "VMs that move", and
  0.5.0's live moves target VMs alone, which drops TCP repair. The move
  plan's CRIU spikes (S-A, S-B, S6, S8, S20, S21) go with it. The condition
  is spike V4: if a VM can't be snapshotted on one node and restored on
  another, CRIU comes back as the only way to keep memory. `MoveRecord` keeps
  its `mode` field either way, so nothing is designed out.

  What it costs: keeping memory needs KVM. A cluster on M1 or M2 Macs, on
  cloud VMs without nested virtualisation, or on machines as small as the
  Wyse gets cold moves only, and an app has to switch to the VM runtime and
  pay its fixed memory to get the feature. Cold moves already cover the
  database with a volume, so the group left out is memory-only apps on hosts
  without KVM.

### Still open

1. **The Apple runtime.** The VM research brings it back in the VM apps
   release (F10, #367). It's still switched off, no CI job runs it, and
   hosted Apple runners can't nest virtualisation. Does it stay with 0.4.4,
   or go to Later so that it can't hold the Linux VM runtime?
2. **Where OIDC login goes.** We've put it in 0.4.2; the maintainer agreed to
   plan it, not yet to that slot.
