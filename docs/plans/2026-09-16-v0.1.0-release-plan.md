# Reliaburger 0.1.0: from laptop to working cluster

Review date: 16 September 2026. Baseline: `282e430` (PR #164).
Status: proposed release plan; no installer or release has been published.

The core platform exists. The release work is to package it, make its first
run reliable, close the remaining correctness gaps, and prove the actual
downloaded product works. Completing every ambition in the whitepaper would
make 0.1.0 an indefinite project. We need a smaller, explicit release contract.

## What this review establishes

This review inventories the roadmap, progress checklist and all 42 existing
plan/review documents, follows the later hardening records, and inspects the
current setup, dev-cluster, release, runtime, security, diagnostics and test
paths. It is a targeted release-readiness review, not a fresh line-by-line
audit of every subsystem.

Evidence categories used below:

- **Source-confirmed:** inspected in the current implementation.
- **Recorded:** reported by an earlier audit/progress entry; requires fresh
  verification before treating it as a current defect or closing it.
- **Proposed:** new release behaviour and acceptance criteria.

The working tree was clean at the start. No live cluster was created and no
privileged Linux, Apple Container or release-candidate acceptance was run.
The test result for the existing setup unit tests is recorded at the end.
Web checks could not retrieve either `https://reliaburger.com` or the configured
`https://releases.reliaburger.dev/metadata.json`; this does not establish that
either host is down. Domain ownership, hosting and available release assets
remain deployment checks.

## The proposed release contract

0.1.0 is an early release for development and small, trusted clusters. It runs
real OCI workloads, persists desired state, recovers after node restarts,
supports service discovery and ingress, and exposes useful logs, status and
diagnostics. It is not a claim of production readiness at 5,000 nodes or strong
isolation between mutually untrusted cluster administrators/workers.

Make the supported path Linux + rootful runc on cgroup v2. On laptops, use
managed Linux VMs so macOS and Linux users exercise the same container data
plane. Reuse the existing Lima integration. Lima supports both macOS and
Linux and distributes binaries; Linux VM prerequisites differ from macOS,
so pin and test the chosen driver and version rather than assuming an empty
host already has them ([installation](https://lima-vm.io/docs/installation/),
[VM drivers](https://lima-vm.io/docs/config/vmtype/)).

Proposed initial qualification matrix:

| Host | 0.1.0 path |
| --- | --- |
| Apple silicon macOS | Native Relish + managed Linux aarch64 VMs; primary laptop gate. |
| Linux x86_64 | Native Relish + managed Linux VMs for quickstart; documented native rootful Bun deployment. |
| Linux aarch64 | Linux agent artefact; qualify native deployment and VM host support separately. |
| Intel macOS | Build native Relish; advertise support only after the cold-install gate passes on real hardware. |
| Native Apple Container | Experimental until mounts, config files and published ports are implemented or explicitly refused. |
| ProcessGrill | Explicit lightweight demo/test mode; never silently substitute it for a container cluster. |
| Windows/WSL | Deferred from the initial support promise. |

Default quickstart should produce **three Linux nodes**, matching the existing
dev command and providing real quorum/failover behaviour. Offer one node as an
explicit low-resource option; label it accurately and do not use it to claim
three-node timing. The existing default budgets 6 GiB guest RAM plus host and
VM overhead. Measure the actual footprint before setting minimum requirements.

Success means all three nodes are healthy, a leader and quorum exist, a
digest-pinned sample OCI application returns the expected response through
host-accessible ingress, and host `relish status`, `logs` and the dashboard
work without `limactl shell` commands. An empty VM or a listening API is not
the finish line.

## Source-confirmed release blockers

| ID | Finding and evidence | Required outcome |
| --- | --- | --- |
| R01 | `.github/workflows/build.yml` packages only Linux aarch64/x86_64 raw binaries and PDFs. No installer, macOS artefacts, signature envelopes or metadata publishing step. | Ship a complete, versioned installation channel for both agent and CLI. |
| R02 | `src/relish/setup.rs::install` requires signed `PlatformArtifact` metadata; `src/upgrade/metadata.rs` has one binary per platform, implicitly Bun. `src/relish/upgrade.rs` defaults to a `.dev` host. | Align installer, Bun upgrades, CLI distribution, asset naming and canonical URLs; preserve old metadata readers or version the new schema explicitly. |
| R03 | `build.rs` writes BPF objects to Cargo's output directory and embeds that directory path. `OnionEbpf::load` reads files from disk; release packaging copies only executables. | Embed BPF bytes or ship/install a version-matched BPF bundle. Prove loading on a host with no build tree. |
| R04 | `setup --yes` takes the default “no” for starting Bun. Interactive start passes `--config` only, not `--cluster`; setup generates no cluster PKI/enrolment flow. | An explicit quickstart operation must install, configure and start a real cluster with no unanswered stdin prompts. |
| R05 | `dev::create` requires installed Lima, creates/boots VMs serially, provisions via apt, then builds Linux binaries in a source-mounted build VM unless both binaries are supplied. | Download verified prebuilt assets. No Rust toolchain, source checkout or compilation on the normal path. |
| R06 | Dev-node config explicitly uses `require_mtls = false` and `allow_insecure_cluster = true`. DNS/ingress/eBPF are not enabled by that template. | Generate enrolled secure nodes and the services needed by the demo. Do not reuse the plaintext dev template as the public quickstart. |
| R07 | `BunClient::health` accepts any HTTP status. Setup's health wait ends in `Ok(())` even when nothing responds. Dev create sleeps eight seconds and treats council output as best-effort. | Check identity/version and structured readiness, retain the overall deadline, and return non-zero on failure. |
| R08 | Dev create saves cluster state late, launches via `nohup`, regenerates security material on retries, and directs users to query from inside node 1. | Durable operation state, stable identity on retry, supervised guest services, host endpoint/context and lifecycle ownership. |
| R09 | `AppleContainerGrill::create` translates env/resources/command but not `spec.mounts` or port mapping. | Fix before promoting native Apple, or reject unsupported specs and keep it experimental. |
| R10 | Pickle handlers buffer up to 512 MiB per request (`src/pickle/api.rs::MAX_REQUEST_BYTES`), explicitly without an aggregate memory bound. | Stream pushes and bound concurrent upload resources; test under the laptop VM memory budget. |
| R11 | CI tests source builds, including privileged Linux and multi-node suites. It does not install and exercise the final published artefacts from a clean laptop. | Add release-artefact and cold-install gates; retain the existing source gates. |

The cross build installs clang/BPF headers on the runner but invokes `cross`
inside its build environment. There is no checked-in `Cross.toml`. Treat the
availability of those tools and target headers inside cross, and the minimum
glibc baseline of produced binaries, as release-build verification tasks, not
as proven failures from this source review.

## The installation experience

Proposed public command, **not available yet**:

```sh
curl -fsSL https://reliaburger.com/install.sh | bash -s -- --quickstart
```

Keep the homepage a normal website and give the script a stable explicit path.
The script should be small: platform detection, pinned-version resolution,
download/verification, atomic installation of Relish, then dispatch to its
quickstart flow. Extend `relish setup` with an explicit `--quickstart` mode
instead of silently changing the established `setup --yes` start semantics.
Retain installation-only and version-pinned modes for automation.

The initial script and first verifier are rooted in HTTPS delivery. A checksum
downloaded beside a binary is not an independent signature verification. Specify
how the bootstrap checks the release signature using a pinned public key and
an available verifier on each supported platform; fail if verification cannot
run. Reuse the existing Ed25519 release-key trust for subsequent assets. Public
installation requires the project signature; operator-specific second signatures
belong to deployments that configure that policy. The current setup already
uses project-signature verification without requiring an operator signature.

Install into a managed directory without replacing an unrelated `bun` executable
(Bun JavaScript is an obvious collision). Invoke managed Bun by absolute path.
Handle PATH for both the current run and subsequent terminals explicitly. Do
not run the downloaded bootstrap wholesale under sudo; scope any prerequisite
installation privileges, or keep rootful operations inside managed VMs.

The Rust flow owns progress, bounded retries, persistent checkpoints and cleanup:
preflight → verified assets → VMs → security enrolment → service readiness →
sample deployment → HTTP proof. Re-running it must resume the same cluster,
not rotate its CA or adopt unrelated VMs. Save owned resource IDs before each
external step. Use private temporary directories for secrets and remove guest
staging copies as well as host copies.

Preflight must cover CPU architecture, supported OS/VM driver, virtualisation,
available RAM/disk, port conflicts, proxies and download reachability. Bootstrap
dependencies from pinned verified assets or produce one actionable error. A
missing runtime must never become an unnoticed ProcessGrill fallback.

Provide host CLI connection configuration and authenticated dashboard access
without putting bearer tokens in URLs. Forward only the intended localhost
ports. Print the sample URL and the exact status/log/stop/start/destroy commands
for this cluster. Uninstall must distinguish binaries from cluster state and
volumes; preserving data should be the default. Test sleep/wake and a changed
VM address as well as ordinary stop/start.

### Making five minutes measurable

Treat five minutes as an acceptance target until measured. Start the clock
before the first installer byte downloads and stop after successful sample
HTTP plus healthy cluster evidence. Include prerequisite and image downloads;
report human interaction time separately. Test with empty Reliaburger/Lima/image
caches on documented hardware and network conditions.

An initial engineering budget is 20s preflight, 90s downloads, 100s VM boot,
45s enrolment/convergence and 30s deployment/probes: 285s total. These are budgets,
not measurements. Publish artefact sizes and timings. On a 50 Mbit/s connection,
each 100 MB already costs about 16s before protocol overhead.

The likely prerequisite is a small, versioned guest image with runc, nftables,
network tooling and required guest agents preinstalled. Cache it once per
architecture and clone disks; boot with bounded concurrency. Preserve independent
VM state and node identities. Include image provenance, checksums, update policy
and redistribution notices. Do not download Rust or run apt upgrades in the
critical path. Measure a prototype before investing in a custom image pipeline.
If cold three-node runs cannot meet the target, optimise or narrow the published
hardware/network promise openly; do not substitute warm-cache timings.

## Remaining correctness work

Promote the following August “Low” items into the release work because they
affect first-run trust or test evidence:

- Source-confirmed: health status checking; swallowed fresh-council initialise
  errors (`cluster/runtime.rs`); production HTTP-client construction panic;
  Apple mount handling; Pickle buffering. Reuse HTTP clients for probes and
  distinguish local setup errors from workload refusal.
- Recorded, recheck and fix: setup/startup filesystem panics; SSE UTF-8 chunk
  corruption; TUI logs mixing between app targets; dashboard desired-count
  reporting; logs-export errors and misleading webhook acceptance.
- Recorded, strengthen before acceptance: deployment history tests that only
  assert non-empty history, single-shot ingress checks, swallowed cluster-instance
  collection errors and missing shared deadlines in testkit waits.
- Source-confirmed: the auth route-matrix guard compares paths but not methods.
  Extend it and verify runtime refusals for both reads and mutations.
- Recorded residual: concurrent node-kill requests can race the observed quorum
  window. Verify it with a concurrency test; fix with cluster-wide reservation
  or keep that operation unavailable in the released supported profile. Serial
  test execution alone is not a server-side safety fix.

Audit the rest of the Low groups once, with dispositions. Do not spend the release
rewriting every helper or splitting large modules. Dead code should either be
removed in a small safe change or explicitly deferred; it should not become an
excuse to introduce a second implementation of an already-working feature.

## Ordered delivery plan

Each numbered item can span small PRs. Write failing behaviour/acceptance tests
first, then implementation, then documentation. Preserve the roadmap's dependency
order; this is closure and release integration of completed phases.

1. **Release baseline and scope.** Reconcile stale checklists, specify support
   and compatibility limits, run the existing CI matrix on the pinned commit,
   and establish cold-start timing/size measurements. Deliver a current failure
   list with commands and evidence, not historical test counts.
2. **Correctness and trustworthy readiness.** Fix R07/R10 and the promoted
   residuals. Tests must prove that 404/500 or an unrelated server cannot count
   as Bun, a failed bootstrap returns non-zero, streaming stays memory-bounded,
   and failed attempts retain actionable diagnostics.
3. **Release artefacts and signing.** Build Linux agents/CLI and native macOS
   CLI, resolve BPF packaging and cross dependencies, publish versioned assets,
   manifests, signatures and checksums from the same commit. Use `--locked`,
   record build identity, pin the tested toolchain/runtime baseline and protect
   release signing. Verify relocated binaries with no source/build tree. Test
   tampered/truncated assets, wrong platform/version and interrupted downloads.
   Keep Bun's existing upgrade metadata compatible or explicitly migrate it.
4. **Managed laptop cluster.** Add a release-assets path to the existing Lima
   lifecycle, explicit contributor source-build mode, stable secure bootstrap,
   guest service supervision, host access and resumable ownership. Prove retry
   at every stage, a second invocation, port collision, stopped/restarted VMs,
   and cleanup limited to owned resources. Optimise the cold path using measured
   image/boot costs.
5. **Public bootstrap and first success.** Implement the small installer and
   `setup --quickstart`, install-only/pinned-version/uninstall flows, sample app,
   authenticated dashboard connection and useful failure output. Test piped
   stdin, no TTY, missing dependencies, PATH collision, network loss and corrupt
   assets using controlled fixtures before hosted smoke tests.
6. **Release-candidate acceptance.** Exercise the exact downloadable candidate
   on the supported host matrix and three independent Linux VMs. Fix failures,
   then promote those same bytes and publish the documentation. A rebuild after
   testing needs another artefact check.

The largest uncertainty is cold VM/dependency delivery, followed by making the
existing dev lifecycle resumable and secure. They should be prototyped before
promising a release date. Finishing the whole whitepaper is not on this critical
path.

## The release gates

- [ ] Existing formatting, all-feature clippy, default/no-default tests,
  doctests, executable examples and fresh dependency audit pass.
- [ ] Provisioned Linux rootful/rootless, cluster, slow and upgrade suites pass
  on the release commit. Review the existing advisory exceptions; their current
  next review is **18 November 2026**, not the stale August date in older plans.
- [ ] Clean-host installation verifies and runs the actual signed candidate,
  including relocated BPF assets and native macOS CLI.
- [ ] Cold three-node quickstart completes inside 300 seconds under published
  reference conditions in repeated runs; keep raw per-stage measurements and
  failures. Record warm-start timings separately.
- [ ] The sample app works from the host; replicas, DNS, ingress, logs, exec,
  health recovery, rolling deploy and rollback behave as documented.
- [ ] Node/leader loss and restart recover desired state without duplicate
  workloads; a volume survives restart on its owning node. Explicitly document
  that local volumes are not distributed storage or automatic data failover.
- [ ] Anonymous/wrong-scope API and registry requests, wrong CA and replayed
  join tokens are rejected. Required policy capabilities are observed live.
- [ ] Registry push/pull, digest checks, restart persistence and eventual
  replication work with the real authentication path. Do not claim synchronous
  replicated durability on push acknowledgement.
- [ ] Run the Phase 15 catalogue, diagnostics, benchmarks and appropriate
  opt-in chaos acceptance with server-owned leases on the supported runc profile.
  Record refusals/unknowns honestly; fix required-capability gaps rather than
  counting them as passes. Verify cleanup after client death and leader change.
- [ ] Stop/start, interrupted setup, VM reboot, uninstall and reinstall preserve
  or remove exactly the documented state. A sustained run covers reconciliation,
  log/metric retention and certificate renewal/hot reload using targeted time
  controls where waiting for expiry is impractical.
- [ ] Release tag, Cargo version, `--version`, metadata and installed asset
  identity agree. Cargo already says 0.1.0; that is not evidence of a published
  functional release. Define the migration policy for existing development
  state and mixed binaries; reject unsupported combinations without destroying
  data. Do not promise rollback across incompatible persistent-state migrations.

## What can wait

PromQL, remote read, extra rollup tiers, ACME automation, Franchise, TC
delay/bandwidth faults, rootless cgroup delegation, a worker/master-key trust
split, large-scale performance claims and broad internal module reorganisation
are not required for this release. Advertised unsupported operations must fail
clearly; known data-loss or authorisation defects cannot be deferred by relabelling
them experimental. Native Apple runtime parity can follow the Linux VM path.
