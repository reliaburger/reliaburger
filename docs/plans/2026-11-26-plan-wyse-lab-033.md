# Plan: the 0.3.3 Wyse lab, in one session

The maintainer decided on 25 November 2026 to skip that evening's lab and
run one lab once every 0.3.3 issue is in, so the whole release is tested on
the hardware at once. This is that lab's run sheet: what to do, in what
order, what each step proves and what to write down. It runs on three Dell
Wyse 3040s, as the [Wyse record](../qualification/2026-11-20-wyse-3040.md)'s
earlier phases did, and fills in that record's "S6: go or no-go" section.

## When

The Studio builds the lab image from `release-1-3-3` once #2151
(the console's invaders and kill mode), #2337 and the owner-record scrub
have merged, and tells the laptop and the maintainer. Its estimate is
Friday 27 November, morning. The lab follows the build. The steps below
take about 3½ hours for one person with one monitor and keyboard; the
times in each heading are estimates.

Step 11 changes a unit's firmware setup, so it comes last. Steps 8 and 9
reboot nodes many times, so they come after the steps that need a settled
cluster.

## Before the lab (no hardware)

- The laptop downloads the lab build's `appliance-x86_64` and
  `appliance-x86_64-next` artifacts into a new `~/wyse-lab/<build>/art` and
  `next`, checks their `SHA256SUMS`, and builds `relish` for the Mac at the
  build's commit. Use that `relish` for every step, not the one on `PATH`.
- Write down the three versions: the lab image, the next good version and
  the broken one (`next/` holds both, two build numbers apart).
- The maintainer brings up the lab network as before (the Mac's dnsmasq
  hands out 10.77.0.11–13; `relish netboot --mode-dhcp-proxy` answers PXE
  only). The laptop doesn't touch it.
- Serve `next/` for steps 9 and 10: `python3 -m http.server 8000 --directory ~/wyse-lab/<build>/next`, and set
  `channel=http://10.77.0.1:8000/releases/download/os-channel/os-channel.json`.
- A stopwatch, or the laptop's clock, for T0 and T1 and the fallback.

## 1. Install with boot logs (about 20 min)

```sh
sudo relish netboot ~/wyse-lab/<build>/art --interface en9 \
  --mode-dhcp-proxy --stream-logs --reinstall
```

Power on all three units and press F12 for the PXE entry (eMMC is still
first in the boot order). Write T0 at the first power-on.

- [ ] Each unit's installer lines appear in the `--stream-logs` output, from
  the kernel to `installed`.
- [ ] Each unit reboots from the installer by itself, and its installed OS's
  boot lines stream too (#2163: three warm reboots).
- [ ] Each unit shows its claim key on screen. Time from power-on to the key.

If a unit hangs on the warm reboot, note how far its streamed shutdown got,
then hold the power button and go on. That's #2163 reproduced, with logs.

## 2. Claim (about 10 min)

```sh
relish machines
relish machines claim ~/wyse --create --name wyse --faults \
  --ssh-key ~/.ssh/id_ed25519.pub
```

Compare each claim key with the unit's screen. `--faults` lets the cluster
take Smoker faults, which steps 5 and 6 need.

- [ ] T1: `relish nodes` shows three alive nodes and `relish council` a
  leader. Write T1 − T0.
- [ ] SSH works on all three: `ssh root@10.77.0.1{1,2,3} true` (#2165).

## 3. Node pressure after a cold boot (about 5 min)

Straight after the claim, before applying anything, on each node:

```sh
ssh root@<node> cat /sys/fs/cgroup/cgroup.subtree_control \
  /sys/fs/cgroup/reliaburger-chaos/cgroup.subtree_control
curl -s --cacert ~/wyse/root-ca.crt -H "Authorization: Bearer $RELIABURGER_TOKEN" \
  https://<node>:9117/v1/capabilities
```

- [ ] Both files list `cpu` and `memory` on every node.
- [ ] `/v1/capabilities` shows `node_pressure` available on every node.

Since #2325, reading `/v1/capabilities` writes nothing, so a pass here means
Bun's start-up enabled the controllers.

## 4. The console (about 20 min)

On each unit's monitor, the ten checks from the console's review (#2150):

- [ ] The layout fits 80×25, with no wrapped or cut lines.
- [ ] The font draws every glyph (borders, arrows, sparklines).
- [ ] The colours are readable.
- [ ] The keys move between the tabs; unplugging and replugging the
  keyboard keeps them working.
- [ ] Before the claim, the claim key was legible (step 1).
- [ ] The Cluster tab says HEALTHY.
- [ ] Kernel messages on the screen clear within about 10 s.
- [ ] The screen doesn't blank (`consoleblank`).
- [ ] Idle CPU on each tab is low (`top` over SSH).
- [ ] With Bun stopped (`systemctl stop reliaburger` on one node), the
  console falls back to the old screen; start it again after.

## 5. Invaders (about 20 min)

Apply a workload with a few instances per node first:

```sh
relish apply examples/<burger or nginx config> --wait
```

On one unit, press `7` for the invaders tab.

- [ ] One invader per app instance on this node, each labelled with its
  instance; the top line says kill mode is off.
- [ ] With kill mode off, a hit pops the invader and nothing else:
  `relish fault list` and `relish events` show nothing, the instance keeps
  running.
- [ ] Turn kill mode on: `relish os settings`, then `relish os set` with a
  file holding `[appliance] console_chaos = true`. The top line says on.
- [ ] A hit kills that instance: it shows in `relish fault list`, `relish events`
  and `relish audit` as injected by the console, and the app reschedules.
- [ ] Turn kill mode off again; a hit is harmless again.

## 6. The chaos suite (about 10 min)

```sh
relish test --chaos --yes
```

- [ ] It starts with no Bun restart and runs the pressure cases (#2242).
  Write the pass, fail, skipped and unknown counts.

## 7. Boot logs on running nodes (about 15 min)

```sh
relish machines logs --interface en9 --dir ~/wyse-lab/<build>/art &
relish os boot-logs
relish os boot-logs --to 10.77.0.1 --node <node>
ssh root@<node> systemctl reboot
```

- [ ] The node's shutdown and boot lines arrive at the listener, and it's
  back as alive.
- [ ] `relish os boot-logs --to` an address with no route from the nodes
  warns, quoting the node's reason, and doesn't claim success (#2323).
  On the node, `cat /sys/kernel/config/netconsole/reliaburger/enabled`
  shows what happened.
- [ ] `relish os boot-logs --off` stops it; a reboot then sends nothing.

Leave streaming on to the laptop for steps 8 and 9.

## 8. Warm reboots in a loop (about 25 min)

On one unit, ideally the one that hung on 20 November:

```sh
for i in $(seq 1 10); do
  start=$(date +%s)
  ssh root@<node> systemctl reboot
  sleep 20
  until ssh -o ConnectTimeout=3 root@<node> true 2>/dev/null; do sleep 5; done
  echo "reboot $i: $(( $(date +%s) - start )) s"
done
```

- [ ] All ten come back by themselves. Write each time. A hang is #2163:
  note the streamed lines, then power-cycle it.

## 9. The fallback (about 30 min)

**A broken update.** On one node, stage the broken version and reboot:

```sh
ssh root@<node> /usr/lib/reliaburger/os-stage \
  http://10.77.0.1:8000/releases/download/os-<broken>-x86_64 <broken>
ssh root@<node> systemctl reboot
```

- [ ] Two failed tries stream, each giving up by about 150 s after its
  kernel starts, then the node is healthy on the old version by itself.
- [ ] Time from the reboot to healthy on the old version: **≤ 10 min**.
  The model says about 8 min 20 s. Write the per-try times from the
  streamed lines.

**A link that never comes up.** On another node, stage the next good
version, reboot, and pull its network cable as soon as the reboot starts.
Plug it back in when the second try's kernel lines start, or after about
5 minutes.

- [ ] Both tries fail with `no IPv4 address after 150 s`, and the node
  falls back to the old version by itself (#2245).

## 10. The cluster OS update (about 20 min)

```sh
relish os list --channel "$channel" --key next/lab-signing-key.pub.pem
relish os upgrade --channel "$channel" --key next/lab-signing-key.pub.pem
relish os status
```

- [ ] One node at a time, all three on the next version, the workload
  moving off each node before its reboot. Write the time per node.

## 11. Network-first boot order (about 20 min)

On one unit, in the firmware setup, put the network first and the eMMC
second.

- [ ] With `relish netboot` serving: the installed machine gets `exit 1`
  and the firmware moves on to the eMMC. Time the boot.
- [ ] With no netboot server at all: how long PXE waits before it tries the
  eMMC. Time the boot.
- [ ] Either make network-first the lab checklist's default (if both boot
  without help and the delay is acceptable), or write down why eMMC-first
  stays. Put the unit back as it was after.
