candidate failed on, why, and the fix that went into the next one. The
per-run evidence lives in the records this page links; this page is the map.

> 12-hour jobs final (run 2, whose only failures are known harness artefacts 3
> and 4, [below](#the-12-hour-jobs-final-run-2)) and 25 runs of every power-cut
> and reboot lane.

## The 12-hour jobs final, run 2

Run 2 ran on candidate 8 with the harness at
[`c2beb891`](https://github.com/reliaburger/reliaburger/commit/c2beb891) (main
after [#986](https://github.com/reliaburger/reliaburger/pull/986)), from 05:36
to 17:36 UTC on 16 October. It completed all 12 cycles. Job qualification fast
run 3 had already passed on this candidate, and #986 changed only how Lima
forwards ports, so the fast tier wasn't run again.

The run recorded 15 failures. The maintainer classified all of them as known
harness artefacts (the [plan's list](../plans/2026-09-25-v02-sustained.md#4-pass-and-fail)),
and the run's evidence was replayed with the classifications through
`scripts/release/sustained_check.py` at `c2beb891`:

- **Failures 1–12, artefact 3** (maintainer decision, 16 October 2026). With
  `LIMA_SSH_PORT_FORWARDER=true`, Lima sets up each port with a single
  `ssh -O forward` and never retries a failed one. After upgrade walk 3,
  node 3 committed the soak build (`wtf` shows all three nodes on it), but
  the host couldn't reach its API, from 18:58 to 19:08 +08 (failure 1).
  After a 153 s power-off, node 1 rebooted and served the cluster (council
  3/3, nothing critical), but its forwarded API and ingress refused on the
  host (ingress `000` in 0.2 ms, empty diagnostics) until upgrade walk 4
  restarted Bun 50 minutes later (failures 2–12). The job controller fell
  back to node 2 for every request in that window, and that's what pushed
  node 2's Bun over the `leak-rss` ratio (failure 8). Node 2's host agent
  later logged the same `failed to set up forwarding … exit status 255`.
  The earlier host-agent logs were overwritten when the VMs restarted
  ([#987](https://github.com/reliaburger/reliaburger/issues/987)).
- **Failures 13–15, artefact 4** (maintainer decision, 17 October 2026). The
  job controller allows 256 runs per campaign (`MAX_RUNS` in
  `scripts/release/job_soak.py`), sized for the fast tier. It reached 256 at
  16:05 UTC, about 10.5 hours in, and from then on it prepared no runs and
  polled none: every batch's `observed_at` stays at 1792166725. Failures 14
  and 15 (`runc has no accepted progress`) follow from that.

The replayed record still reads FAIL on one gate, "mixed job campaign and
positive drain", because the checker computes that gate from the job
snapshot rather than from the failure rows. All six of its items are
artefact 4. When the controller stopped polling, its last three batches
stood at 475/512, 468/512 and 1,047/1,049 chunks. Bun keeps a finished task
array readable for an hour and then prunes it (`TERMINAL_RETENTION_SECS =
3600`, [`src/meat/task_array_store.rs:28`](https://github.com/reliaburger/reliaburger/blob/cc5f6439/src/meat/task_array_store.rs#L28)).
The drain came about 85 minutes later, so its cancels got HTTP 404 for
arrays that had finished and been pruned, which is correct. The controller
never saw them finish, so the drain timed out. The harness's exit 1 is that
drain exit, after the twelfth cycle.

What the run shows:

- **Throughput:** 4,600.3 accepted a second against the 1,390 target. That's
  145.8 million process, 52.4 million shared-runc and 60,369 runc successes,
  with job load covering about 10.5 of the 12 hours.
- **Memory:** Bun stayed within its targets. The worst was node 2, at
  226.89 MiB steady and 400.08 MiB peak, against 384 MiB (512 MiB on node 1).
  There was no OOM kill.
- **Batch wall time:** a 1,048,576-task array took 264 s at the median and
  1,167 s at worst, against a 600 s target that's recorded, not gated.
- **Everything else passed:** every renewal, rotation and reload gate.
  Nothing lost data, and no failure came from the product.

The harness fixes are in 0.2.1: drop the SSH forwarder with the Lima 2.2.1
bump ([#983](https://github.com/reliaburger/reliaburger/issues/983)), detect a
node cut off from the host
([#987](https://github.com/reliaburger/reliaburger/issues/987)), and size the
run budget from the schedule
([#989](https://github.com/reliaburger/reliaburger/issues/989)).

## Known issues shipped in 0.2.0

- The quickstart pins Lima 2.1.0. Before 2.1.3, any user in a QEMU-driven VM
  (the Linux quickstart) can reach the guest agent's socket and become root in
  the VM (CVE-2026-53657), and the gRPC port forwarder leaks a socket per
  forwarded connection, so a long-running quickstart's API node slowly loses
  memory. Both are fixed by bundling Lima 2.2.1 in 0.2.1
  ([#983](https://github.com/reliaburger/reliaburger/issues/983)). The V02
  tiers and the jobs fast tier ran on the default gRPC forwarder; the jobs
  final's run 2 ran with `LIMA_SSH_PORT_FORWARDER=true`
  ([#986](https://github.com/reliaburger/reliaburger/pull/986)), so it shows
  Reliaburger under 12 hours of job load, not Lima 2.1's forwarder.
- Bun has the default OOM score, so it is the kernel's first choice on a
  memory-starved node ([#984](https://github.com/reliaburger/reliaburger/issues/984), 0.2.1).
