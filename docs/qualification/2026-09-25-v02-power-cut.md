# V02 physical-crash lanes: power cuts on a disposable VM (25 Sep 2026)

Lane C of the V02 plan: storage power-cut fixtures for C03 (exporter
checkpoint and cross-process lock) and C11 (`LocalLeaseStore`), plus the
existing OCI and discovery reboot qualifications for C47. Every iteration
hard-powers the VM off with `limactl stop --force`, which discards the guest's
page cache the way a real power loss would.

**Result: the C03 fixture found a data-loss bug.** Local exports weren't synced
before the checkpoint acknowledged them, so a power cut left every recent
export as a zero-byte file while the pruners had already deleted the sources.
The fix (sync local uploads; `local_destinations_sync_uploads_before_acknowledging`)
is in the same pull request. After it, every lane passed.

The shared development VM (`reliaburger-test`) wasn't touched; the driver

above 12%; they don't prove a rare failure absent.

Before the 25-run C03 record, a first 25-run attempt on the fixed build passed
seven iterations and stopped at the eighth, when Lima couldn't restart the VM
("Invalid virtual machine configuration. The storage device attachment is
invalid", straight after the forced stop). That is an environment failure: a
manual `limactl start` worked, and running the verify phase against that
iteration's directory passed (162 objects, 153 sources pruned, nothing lost).
The driver now retries a failed start once after 10 s and marks the row
`PASS (VM start retried)`. No row in the records below needed it.

### C03: exporter

Four workers per iteration: a generator that flushes real Parquet through
`LogStore` and publishes it into the exported directory, and three exporters
sharing one `_export_checkpoint.json` and `_export_checkpoint.lock` against a
`file://` destination. Exporter 0 only exports (like `relish logs-export`);
exporters 1 and 2 export then prune at 16 KiB (like Bun's disk-pressure
tick). Each worker appends finished operations to an fsynced ledger.

Verify checks that the checkpoint parses; every acknowledged and every
checkpointed export is at the destination byte for byte against a synced
reference copy; every published file is either still in the source unchanged
or at the destination (nothing pruned unexported); the lock can be taken; a
fresh export of new data succeeds; and DataFusion reads every destination
object with the expected row count.

**Before the fix**, four runs, all failing the same way:

| Cut after (s) | Generated | Acknowledged | Acknowledged but empty at destination | Sources pruned and lost |
|---|---|---|---|---|
| 5 | 67 | 67 | 67 | 59 |
| 4 | 53 | 53 | 53 | 45 |
| 6 | 77 | 77 | 77 | 69 |
| 12 | 171 | 170 | 170 | 162 |

Every lost object was present with the right name and 0 bytes. The checkpoint
itself was intact. `object_store::parse_url` builds `LocalFileSystem::new()`,
whose `fsync` option defaults to off, so the upload's data and rename weren't
durable when the checkpoint (which *is* synced) recorded it as exported. The
pruners then deleted the only good copy. With ext4's 30-second commit
interval, any export in roughly the last half-minute before a power loss was
at risk.

**The fix** builds the local store with `with_fsync(true)` in
`ketchup::export::parse_destination`, which covers both log export and the
metrics exporter (both go through `export_logs`). A portable regression test
checks the configuration. An experiment with the same change passed three
power cuts first; the 25-run record on the fixed build then looked like this:

| Cut after (s) range | Runs | Generated per run | Pruned per run | Staged object leftovers | Stale checkpoint temporaries |
|---|---|---|---|---|---|
| 1–20 | 25 | 18–268 | 10–260 | 0 | 0–1 |

The same class of risk exists wherever Bun uploads through
`object_store::parse_url` to a `file://` URL and then relies on the upload:
the snapshot uploader (`src/bun/snapshot_worker.rs`), council backups
(`src/council/backup.rs`) and the metrics object-store backend
(`src/mayo/store.rs`). This record doesn't qualify them; they need their own
fixtures.

### C11: lease stores

Three workers, each owning one store file (`test-leases.json`,
`node-test-leases.json`, `soak-test-leases.json`) in one shared directory,
loop over create, renew, begin cleanup and finish cleanup. Each writes a
`begin` line before and an `ack` line after every operation. Verify replays
each ledger and accepts exactly two states per store: all acknowledged
operations applied, or those plus the single in-flight operation. It also
checks that no store holds another worker's leases (a private temporary
renamed over the wrong file), that the store reopens, and that it accepts and
persists a new create, renew and release.

| Cut after (s) range | Runs | Operations acknowledged per run | In-flight operation landed | Stale temporaries left |
|---|---|---|---|---|
| 1–20 | 25 | 60–3,196 | 4 runs | 0–2 |

Stale `.reliaburger-*` temporaries after a cut are expected (the rename never
happened) and harmless, but nothing removes them from the lease directory.
They're a small follow-up, not a correctness failure.

### C47: OCI and discovery reboots

Both existing scripts ran unchanged against `rb-v02-crash`, 25 times each,
back to back. Every run proved a new boot ID. The first OCI iteration took
295 s because it compiled the `ebpf` test binaries; the rest took 18–20 s
(OCI) and 24–42 s (discovery).
