# 0.3.3 release closure

27 November 2026. How the 0.3.3 candidate was qualified: what each gate run
found, and what follows from it. The per-run evidence lives in the records
this page links; this page is the map.

> **Candidate 1 (`5f21eef6`) is the release candidate.** It passed both
> staged installs, the power-cut and reboot lanes (25 of 25 in every lane),
> the V02 fast tier, the jobs fast tier and the 8-hour jobs final, all clean
> and all at the first attempt. The final ran its whole schedule (10 h
> 15 min: eight cycles, four upgrade walks, both quorum losses, the all-off
> and a quiet tail with every leak checker armed on every node, all ok;
> every fault class settled every time; council history linearizable; no
> data lost) with no failures, and no agent-loop turn went over its 1 s
> budget on any node in any tier.
>
> **Known issues accepted at this gate:** none. #2128, 0.3.0's registry
> deploy stall, didn't recur (the catalogue pulse passed all eight runs in
> the final), but its cause is still unproven and the issue stays open, in
> 0.3.4.
>
> **Hardware: the Wyse lab has not run on this candidate.** No appliance
> image from this candidate has booted on a Dell Wyse 3040 or any other real
> machine for this gate. The maintainer chose to release 0.3.3 without it;
> the lab runs over the weekend of 28–29 November, on the released
> artefacts, and anything it finds goes into 0.3.4. The appliance image built
> from the candidate ([run 45870249187](https://github.com/reliaburger/reliaburger/actions/runs/45870249187))
> passed only `appliance.yml`'s own QEMU tests. The Wyse exit test
> ([#407](https://github.com/reliaburger/reliaburger/issues/407)) stays open,
> in 0.3.4.

## The gate

`scripts/release/release_tier.py --previous v0.3.2 --release v0.3.3 --commit 5f21eef6a`
asks for the full gate. 0.3.3 keeps 0.3.2's wire protocol (61) and state
format (76), so it rolls onto a 0.3.2 cluster in place, but it changes the
agent loop (`src/bun/agent.rs`, `src/bun/agent/app_stop.rs`,
`commands.rs`, `deploy_ops.rs`, `deploy_worker.rs` and 14 more files), and
any change there gets the 8-hour jobs final
([a gate scaled to the release](../releasing.md#a-gate-scaled-to-the-release)).
The gate didn't lean on a nightly through `freeze-check`: every tier ran
on the candidate itself, on the Mac
Studio, from 23:24 GMT on 26 November to 12:57 GMT on 27 November, one after
another from one script. The script logged the host's 1-minute load average
at each step's start and end: 1.4 to 3.5 through the power-cut lanes, the
staged installs and the V02 fast tier, and 5 to 7 through the jobs tiers,
whose three VMs run the job load themselves.

| Gate | Result | Record |

| Staged install, Apple silicon | PASS, 70 s to a ready cluster | [record](2026-11-27-v0.3.3-staged-install-apple-silicon.md) |
| Staged install, Apple silicon (2) | PASS, 87 s | [record](2026-11-27-v0.3.3-staged-install-apple-silicon-2.md) |

| 8-hour jobs final | PASS, 10 h 15 min of soak | [record](2026-11-27-v0.3.3-jobs-final.md) |

Neither staged install needed the installer to restart a VM, unlike 0.3.2's
first: VM boot took 16 s and 20 s.

The final's slowest settle was 83 s, after an upgrade walk; every fault
class's slowest was 55 s or less. The stall watchdog recorded no agent-loop
stall in any of the three soaks. Two recorded, ungated measures are worth
reading: the slowest of 64 million-task arrays took 862 s (median 122 s)
against the September plan's 600 s for one array on a quiet cluster, as
0.3.2's slowest took 831 s; and Bun's worst steady RSS was 214 MiB on a
worker node, against its 384 MiB target.

Before the gate, the Studio ran the quiet macOS `make test-upgrade-node`
loop that the [24 November record](2026-11-24-v02-loops-local.md#rerun) asked
for, on this candidate: 115 of 115 passed, from 17:43 to 23:13 GMT on 26
November ([record](2026-11-26-v02-upgrade-node-macos.md), part of
[#287](https://github.com/reliaburger/reliaburger/issues/287)). The gate
chain waited for it to finish.

against 0.3.2's staging.

## The release build

The train's code is final at candidate 1. The tag goes on the merge of the
gate PR ([#2263](https://github.com/reliaburger/reliaburger/pull/2263)) into
main, which is built again on main and signed with the release key. Main has
nothing the train doesn't, and when this was written the only change on the
train after `5f21eef6` was these records (documentation, the roadmap,
`CLAUDE.md` and `CHANGELOG.md`). So the release build's code is candidate
1's, provided nothing else merges into the train first: the soaks,
the power-cut lanes and the fast tiers carry over, and only the staged
installs run again, on the release build, as for 0.3.2.

The release build, its staging, its staged installs and its promotion
aren't done at the time of writing. The post-release docs PR adds their run
IDs, the release build's `candidate.json` digest and its two staged-install
records here.
