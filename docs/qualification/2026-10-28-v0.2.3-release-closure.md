# 0.2.3 release closure

26–28 October 2026. How the 0.2.3 candidate was qualified: what each gate run
found, what the maintainer decided, and what moves to 0.2.4. The per-run
evidence lives in the records this page links; this page is the map.

> **Candidate 1 (`d387d569`) is the release candidate.** It passed both staged
> installs, the jobs fast tier, the 8-hour jobs final and the power-cut and
> reboot lanes (25 of 25 in every lane). Its first V02 fast run failed on one
> slow `upgrade_verify` turn during a host disk stall; the maintainer accepted
> it as a host stall ([below](#the-host-stall-accepted-for-023)), and the
> re-run on the same candidate passed every check.
>
> **The day run counted 1,807,742,226 host-job tasks in one real 24-hour day
> on three nodes**, 20,920 a second: 1.81 billion against the 2 billion
> target, on a 2023 MacBook Pro. The maintainer accepted the measured number.
> The harness's verdict is FAIL, and the [day-run record](2026-10-28-v0.2.3-day-run.md)
> publishes it unchanged. Bun's memory grew on every node for the whole run
> (still under the job targets; [#1417](https://github.com/reliaburger/reliaburger/issues/1417)),
> node 1's disk filled up near the end
> ([#1418](https://github.com/reliaburger/reliaburger/issues/1418)), and one
> agent-loop turn ran over budget
> ([#1419](https://github.com/reliaburger/reliaburger/issues/1419)). The
> maintainer shipped 0.2.3 with all three documented, to be fixed in 0.2.4.
>
> **Known issue it ships with:** 13 RustSec advisories against `zstd` 0.13.3
> and `zstd-safe` 7.3.0, published on 26 October, reached only through the
> Parquet files Reliaburger writes itself. 0.2.3 ships with a reviewed,
> time-boxed exception
> ([#1367](https://github.com/reliaburger/reliaburger/pull/1367),
> [record](2026-10-26-dependency-exceptions.md)); the fix is
> [#1366](https://github.com/reliaburger/reliaburger/issues/1366) in 0.2.4.
>
> **And one it isn't exposed to:** RUSTSEC-2026-0414 against
> `pulldown-cmark` 0.13.4, published on 28 October, needs an option
> Reliaburger never sets, on Markdown it never takes from anyone else. The
> maintainer kept the candidate rather than rebuild it
> ([record](2026-10-28-dependency-exceptions.md)); the fix is
> [#1409](https://github.com/reliaburger/reliaburger/pull/1409).

## The gate

The same gate as 0.2.2: two staged installs, the V02 fast tier, the jobs fast
tier, one 8-hour jobs final (`qualify-jobs-sustained.sh --tier final`) and the
power-cut and reboot lanes, 25 runs each. Two things came first and one after:

- **The throughput benchmark**, on the staged candidate itself, before any
  long tier
  ([#1030](https://github.com/reliaburger/reliaburger/issues/1030),
  [#1031](https://github.com/reliaburger/reliaburger/issues/1031),
  [record](2026-10-27-v0.2.3-candidate-throughput/README.md)). 0.2.3 raises
  `MAX_LEARNED_GRANT_DEPTH` from 16 to 32
  ([#1361](https://github.com/reliaburger/reliaburger/pull/1361)), and the
  maintainer chose to measure that on the candidate rather than on a build
  made for the purpose.
- **The day run**
  ([#1032](https://github.com/reliaburger/reliaburger/issues/1032)), outside
  the gate: 24 hours of host jobs on three nodes, as 0.2.3's headline record
  ([below](#the-day-run)).

The maintainer kept the 8-hour final rather than letting the day run replace
it: the final is a fault soak at 1,390 jobs a second, and the day run has no
faults. Shortening the gate is
[#1363](https://github.com/reliaburger/reliaburger/issues/1363), for 0.2.4.

## The host stall accepted for 0.2.3

0.2.3 fixed the two durable writes that failed 0.2.2's runs: the egress-owners
file ([#1263](https://github.com/reliaburger/reliaburger/issues/1263)) and the
receipt confirmation
([#1340](https://github.com/reliaburger/reliaburger/issues/1340)) now leave a
slow write in flight, and neither failed a 0.2.3 run. A third write did:

| Run | Slow turn | What it waited for | The stall elsewhere |
|---|---|---|---|
| V02 fast, run 1 (23:16:33 GMT, 26 Oct) | node 2: `agent loop turn took 2260 ms in command (upgrade_verify)` | `UpgradeManager::commit`, which appends the upgrade history, garbage-collects old binaries and removes the upgrade marker, all inline on the agent loop | node 3: `a discovery journal write took 4908 ms` in the same second |

That is the host-stall class the maintainer defined for 0.2.2: a slow part on
disk, with a simultaneous multi-second stall on another node, and every other
check passing. The maintainer accepted it on **27 October 2026**, with the fix
in 0.2.4 ([#1381](https://github.com/reliaburger/reliaburger/issues/1381)), and
the fast tier ran again on the same candidate. Run 2 passed, its second
upgrade walk included.

## The day run

Day run 1 used the image's BusyBox and ran about 15,100 a second, half what
the benchmark had measured. The benchmark ran Ubuntu's `busybox-static`, which
costs half as much CPU per process. The maintainer stopped day run 1 after
two hours
([record](2026-10-28-v0.2.3-release-closure/candidate-1-day-run1-stopped.md)),
and [#1386](https://github.com/reliaburger/reliaburger/pull/1386) pinned the
benchmark's BusyBox for the day tier. Day run 2 started at 17:30 UTC on
27 October and ran the full 24 hours on the same candidate
([record](2026-10-28-v0.2.3-day-run.md)).

| Measure | Result |
|---|---|
| Host-job tasks in 24 h | 1,807,742,226 (20,920.0/s) against 2,000,000,000 (23,149/s): **below target**, accepted |
| Billion-a-day floor (11,575/s) | met |
| Last hour against the first | 20,689.6/s against 22,226.6/s, 6.9% slower: **ok** (10% allowed) |
| Per node | 587.1M, 611.8M and 608.8M, all within fair share |
| Errors and lost tasks | none; 1 retry on the host path |
| Bun RSS, steady / peak (worst node) | node 1: 310.9 / 344.5 MiB, under its 512 MiB target; nodes 2 and 3: 290.7 / 321.8 and 281.5 / 315.7 MiB, under 384 MiB |
| `leak-rss` | **failed** on every node from about 7 h in: RSS over 125% of its value at the one-hour mark |

The hourly rate slid from 22,227 to 19,904 a second over the first 14 hours,
then held between 19,900 and 20,700 to the end
([#1403](https://github.com/reliaburger/reliaburger/issues/1403) tracks the
cause).

What the maintainer accepted, and why
([classified in full in the record](2026-10-28-v0.2.3-day-run.md#the-maintainers-verdict)):

- **The total.** 1.81 billion on a laptop whose 12 cores the three VMs fill,
  after the same candidate measured 29,350 a second on three nodes in the
  benchmark. 2 billion is a matter of a host with more cores, not of a fix.
- **Bun's memory growth.** It stayed under the job targets for the whole day,
  and the 8-hour jobs final, the gated leak soak, passed the same checker on
  the same candidate. A slow leak isn't ruled out:
  [#1417](https://github.com/reliaburger/reliaburger/issues/1417) profiles it
  in 0.2.4.
- **Node 1's disk.** Its job instance storage grew to 949 MiB, on a 10 GiB VM
  disk shared with the soak's own exports
  ([#1418](https://github.com/reliaburger/reliaburger/issues/1418)).
- **One slow `follow_up` turn on node 3,** possibly a host disk stall (every
  node logged about one-second journal writes five minutes later), but
  unproven ([#1419](https://github.com/reliaburger/reliaburger/issues/1419)).
