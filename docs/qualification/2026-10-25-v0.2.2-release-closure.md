# 0.2.2 release closure

21–25 October 2026. How the 0.2.2 candidates were qualified: what each
candidate failed on, why, and the fix that went into the next one. The
per-run evidence lives in the records this page links; this page is the map.

> **Candidate 4 (`43baee64`) is the release candidate.** It passed both staged
> installs and the power-cut and reboot lanes (25 of 25 in every lane). Its V02
> fast tier failed twice and its jobs fast tier once, each time on one slow
> agent-loop turn during a host disk stall; the maintainer accepted all three
> as host stalls for 0.2.2 ([below](#host-stalls-accepted-for-022)), with the
> fixes in 0.2.3. Its first 8-hour jobs final failed only because the harness
> asked the job campaign to drain while the hour-8 graceful whole-cluster stop
> was still running ([#1338](https://github.com/reliaburger/reliaburger/issues/1338),
> [below](#run-1-the-drain-clash)). With the harness fixed
> ([#1339](https://github.com/reliaburger/reliaburger/pull/1339)), run 2 on
> the same candidate completed all 8 cycles, drained the job campaign and passed every check
> except one slow agent-loop turn: the same receipt confirmation, in a host
> disk stall that node 3 saw in the same second. That meets the maintainer's
> host-stall rule, which completes the gate.
>
> **Known issue it ships with:** RUSTSEC-2026-0387 (timing variability in
> crypto-bigint 0.5.5), reached only through `age` 0.12's P-256 code, which
> Reliaburger never calls. 0.2.2 ships with a reviewed exception
> ([#1318](https://github.com/reliaburger/reliaburger/pull/1318),
> [record](2026-10-24-dependency-exceptions.md)); 0.2.3 drops crypto-bigint 0.5
> by moving to `age` 0.11.5
> ([#1332](https://github.com/reliaburger/reliaburger/issues/1332),
> [#1333](https://github.com/reliaburger/reliaburger/pull/1333)).

## The gate

The same gate as 0.2.1 ([#991](https://github.com/reliaburger/reliaburger/issues/991)):
two staged installs, the V02 fast tier, the jobs fast tier, one 8-hour jobs
final (`qualify-jobs-sustained.sh --tier final`) and the power-cut and reboot
lanes. The lanes ran 25 times each, as for 0.2.0 and 0.2.1, because 0.2.2
changes how Bun talks to process owners
([#1299](https://github.com/reliaburger/reliaburger/issues/1299)) and moves
more of the agent loop's durable writes.

## Host stalls accepted for 0.2.2

The three Lima VMs on the soak host stall on disk together, for 3 to 5 s,
every few minutes. Most of the agent loop's durable writes already leave a
slow write in flight and carry on (#1100, #1255, #1266). Two still waited on
the loop in 0.2.2, and between them they failed four runs:

| Run | Slow turn | What it waited for | The stall elsewhere |
|---|---|---|---|
| V02 fast, run 1 (18:55 UTC, 24 Oct) | node 1: `agent loop turn took 5555 ms in restart_step: … egress owners write 5513 ms` | The egress-owners file, persisted inline (`persist_egress_owners`) | node 2: `a discovery journal write took 4869 ms` minutes before, and a 500 ms consumer-sync journal turn at the same second |
| V02 fast, run 2 (20:30 UTC, 24 Oct) | node 3: `agent loop turn took 2842 ms in command (confirm_consumer_receipt): journal write 2842 ms` | The consumer journal write behind a receipt confirmation | node 2: `a discovery journal write took 2690 ms` at the same second |
| Jobs fast (21:22 UTC, 24 Oct) | node 2: `agent loop turn took 1429 ms in command (confirm_consumer_receipt): journal write 1429 ms` | The same receipt confirmation | None over a second on the other nodes |
| Jobs final, run 2 (23:12 UTC, 25 Oct) | node 1: `agent loop turn took 3634 ms in command (confirm_consumer_receipt): journal write 3634 ms` | The same receipt confirmation | node 3: `a discovery journal write took 3644 ms` in the same second |

Maintainer decisions:

- **24 October 2026**, after V02 fast run 1: a host stall, which doesn't block
  0.2.2. Fix in 0.2.3 under
  [#1263](https://github.com/reliaburger/reliaburger/issues/1263).
- **24 October 2026**, after V02 fast run 2, for the whole class: for 0.2.2, an
  `agent-loop-turn` failure whose slow part is a disk write, with a
  simultaneous multi-second stall seen on another node and every other check
  passing, counts as a host stall. Each one is listed here.
- **25 October 2026**, the jobs fast tier: accepted as a host stall for 0.2.2,
  although no other node shows a simultaneous multi-second stall.

The 0.2.3 train already leaves the egress-owners write in flight
([#1263](https://github.com/reliaburger/reliaburger/issues/1263),
[#1334](https://github.com/reliaburger/reliaburger/pull/1334)). The receipt
confirmation is
[#1340](https://github.com/reliaburger/reliaburger/issues/1340), also in 0.2.3.

## The 8-hour jobs final

### Run 1: the drain clash

Run 1 ran from 06:19 to 14:20 UTC on 25 October and completed all 8 cycles. Its
only failures were the job campaign's:

```
- job campaign drain deadline exceeded
- job campaign did not positively drain before teardown
```

`qualify-sustained.sh` asked the controller to drain at `end - 120` and the
controller allows 110 s. But a cycle that has started finishes, so the last one
can run past `end`, and an 8-hour final's hour-8 special is the graceful
whole-cluster stop and start. The special began at 14:16:54 UTC and the cluster
was settled again at 14:19:55. The drain was requested at 14:17:27, and its
deadline passed at 14:19:17, so the cluster was stopping, stopped or starting
for the drain's whole allowance. Three long batches still had chunks held on
node 1 that needed the harness's replay acknowledgement, which a stopped
cluster can't take. It's a harness bug, not a product one
([#1338](https://github.com/reliaburger/reliaburger/issues/1338)).

Everything else in run 1 passed:

- **Faults:** every fault, special, upgrade walk and rollback settled, with
  none failed or skipped. The slowest was the quorum loss, at 84 s.
- **Agent loop:** no turn over the 1 s budget.
- **Throughput:** 3,986 accepted a second against the 1,390 target: 84.8
  million process, 29.5 million shared-runc and 65,106 runc successes.
- **Memory:** the worst Bun was node 1's, at 301.43 MiB steady, against 512 MiB.
- **Batch wall time:** 64 arrays of 1,048,576 tasks, 339 s at the median and
  1,352 s at worst, against a 600 s target that's recorded, not gated.
- **Renewals and rotations:** 18 workload identity rotations and 17 node leaf
  renewals per node, 90 ingress reloads.
- **Data:** the volume writer reached ACK 237,742 and the Redis counter 26,600,
  with no writer-lost or writer-regression failure. Nine registry images were
  pushed and verified again.

[#1339](https://github.com/reliaburger/reliaburger/pull/1339) (on `main` after
the candidate) asks for the drain only once the last cycle and its special are
over, and waits up to 150 s for the controller before the final checks and
teardown. The checker now fails a final whose harness never asked for the
drain, and one whose controller stopped before it was asked. The candidate's
product binaries don't change, so run 2 ran on the same candidate with the
fixed harness, as the [pre-1.0 harness-artefact rule](../releasing.md#staging-a-candidate) allows.

### Run 2

Run 2 ran from 15:18 to 23:19 UTC on 25 October, on the same candidate with
the #1339 harness, and completed all 8 cycles
([record](2026-10-25-v0.2.2-job-qualification.md)). The drain started after
the hour-8 graceful stop and start had settled, and the job campaign drained
with nothing missing. It recorded one failure, `agent-loop-turn` (settle
check, 23:12:28 UTC), during cycle 8's disk-full fault on node 1:

```
23:12:07 node-1: a discovery journal write took 1997 ms; the agent loop went on meanwhile
23:12:10 node-1: agent loop turn took 3634 ms in command (confirm_consumer_receipt): journal write 3634 ms
23:12:11 node-3: a discovery journal write took 3644 ms; the agent loop went on meanwhile
```

Node 3 had no fault, and its off-loop discovery write stalled for as long in
the same second; node 2's runtime inventory reads hit their 500 ms deadline
at the same time. It's the host's disk stall again, caught by the one writer
that still waits on the loop
([#1340](https://github.com/reliaburger/reliaburger/issues/1340)). Under the
maintainer's class rule of 24 October ([above](#host-stalls-accepted-for-022))
it counts as a host stall.

Everything else passed:

- **Faults:** every fault, special, upgrade walk and rollback settled, with
  none failed or skipped. The slowest was an upgrade walk, at 65 s.
- **Throughput:** 3,877 accepted a second against the 1,390 target: 82.6
  million process, 29.0 million shared-runc and 63,414 runc successes.
- **Memory:** the worst Bun was node 2's, at 345.66 MiB steady, against
  384 MiB. Node 2's other processes stayed under 200 MiB; that one ran through
  the busiest hours of the campaign.
- **Batch wall time:** 64 arrays of 1,048,576 tasks, 371 s at the median and
  1,421 s at worst, against a 600 s target that's recorded, not gated.
- **Renewals and rotations:** 20 workload identity rotations and 17 node leaf
  renewals per node, 91 ingress reloads, and the job campaign drained with
  nothing missing.
- **Data:** the volume writer reached ACK 239,027 and the Redis counter 26,328,
  with no writer-lost or writer-regression failure. Nine registry images were
  pushed and verified again.

## Known issues shipped in 0.2.2

- Two agent-loop writers still wait inline for a durable write, so a slow
  disk can hold the loop for seconds: the egress-owners file
  ([#1263](https://github.com/reliaburger/reliaburger/issues/1263), fixed on
  the 0.2.3 train) and the consumer receipt confirmation
  ([#1340](https://github.com/reliaburger/reliaburger/issues/1340), 0.2.3).
  The soak saw turns of 1.4 to 5.6 s. Nothing was lost, but every caller on
  that node waits for the turn.
- RUSTSEC-2026-0387, under a reviewed exception
  ([#1318](https://github.com/reliaburger/reliaburger/pull/1318); 0.2.3 drops it).
