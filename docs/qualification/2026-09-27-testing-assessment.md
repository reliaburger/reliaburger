**Assessment:** Reliaburger has substantial tests of real processes, kernel behaviour, ownership recovery and failure handling. Its weakest evidence is concentrated around security-policy composition, GitOps trust/reconciliation, snapshot restore/export, browser behaviour and the machinery that decides whether qualification passed. The main improvement should be to strengthen those contracts and their assertions, rather than maximise the number of tests.

This is static analysis of test bodies, production callers, Makefile/nextest selectors, workflows, benchmarks and checked-in qualification records. No tests, builds, services, Lima commands, VM inspection or workload actions were run. Historical records below describe their own candidates; they say nothing about the currently running release exercise. No new coverage percentage or flake rate was measured. Proposed checks belong in later, independently provisioned work.

## 3. Quality of the test coverage

### What the coverage number does and does not establish

The configured gate is **78.65% portable line coverage**, produced by one default-feature Linux nextest run. The report command tolerates unreadable process profiles because crash tests deliberately kill processes; the Makefile explains this choice. Privileged/ignored suites, browser JavaScript and Python release tooling are not incorporated into that Rust coverage report. No-default-feature and all-feature compilation/linting exist, but that is a different guarantee from executing those configurations. [Makefile:6](https://github.com/reliaburger/reliaburger/blob/0eb6071da897b836d27e19d277a9a8e69a96ccbb/Makefile#L6), [Makefile:97](https://github.com/reliaburger/reliaburger/blob/0eb6071da897b836d27e19d277a9a8e69a96ccbb/Makefile#L97), [.github/workflows/ci.yml:117](https://github.com/reliaburger/reliaburger/blob/0eb6071da897b836d27e19d277a9a8e69a96ccbb/.github/workflows/ci.yml#L117).

There is no basis here for saying “module X has 20% coverage”, or that the overall current result is exactly 78.65%. That is a threshold, not this review's measurement. A portable line can execute without asserting its outcome; an unexecuted Linux-only branch may be protected by a separate privileged test. Report those facts separately.

For a useful future coverage report, retain per-module and changed-line coverage, selected/executed/ignored/platform-excluded test counts, and a short inventory of critical behaviours with their regression tests. Add branch coverage where the chosen tooling supports it. Keep separate results for default/no-default configurations and provisioned suites; do not add percentages from different denominators. Track incomplete crash-process profiles explicitly so coverage movement remains interpretable.

### Specific weaknesses in assertions and test selection

**T01 — A test invokes the function without checking the Linux outcome.** `check_cgroup_v2_on_test_host` discards `check_cgroup_v2()` on Linux. It would still pass if the detector returned the wrong success/error result. This is at most a no-panic smoke check, not validation of detection. Introduce a testable filesystem/probe boundary and assert both v2-present and v2-absent outcomes; keep one provisioned-host check that must succeed. [src/onion/ebpf/loader.rs:477](https://github.com/reliaburger/reliaburger/blob/0eb6071da897b836d27e19d277a9a8e69a96ccbb/src/onion/ebpf/loader.rs#L477).

**T02 — An explicitly selected test can manufacture a pass.** `node_pressure_consumes_capacity_outside_bun_and_cleans_up` is ignored by default, but returns normally if its environment gate is absent. `make test-linux` supplies it correctly, so this is not a claim that the configured CI lane skips the test. Direct or incorrectly provisioned invocations can nevertheless report success without the advertised behaviour. Once selected, require the prerequisite and fail with a useful message. [tests/node_pressure.rs:28](https://github.com/reliaburger/reliaburger/blob/0eb6071da897b836d27e19d277a9a8e69a96ccbb/tests/node_pressure.rs#L28), [Makefile:46](https://github.com/reliaburger/reliaburger/blob/0eb6071da897b836d27e19d277a9a8e69a96ccbb/Makefile#L46).

**T03 — Loop qualification's text and process status disagree.** `loop_summary.py` writes `Verdict: FAIL` for failed/no-run evidence but always returns zero. Its tests assert the report text without asserting failure status. The parser also counts a `<testcase>` with `<skipped/>` as an executed non-failing run, and combined summaries examine only files present rather than an expected lane manifest. Missing artefacts can therefore disappear from the combined denominator. [scripts/release/loop_summary.py:30](https://github.com/reliaburger/reliaburger/blob/0eb6071da897b836d27e19d277a9a8e69a96ccbb/scripts/release/loop_summary.py#L30), [scripts/release/loop_summary.py:104](https://github.com/reliaburger/reliaburger/blob/0eb6071da897b836d27e19d277a9a8e69a96ccbb/scripts/release/loop_summary.py#L104), [scripts/release/loop_summary.py:116](https://github.com/reliaburger/reliaburger/blob/0eb6071da897b836d27e19d277a9a8e69a96ccbb/scripts/release/loop_summary.py#L116), [scripts/release/test_loop_summary.py:43](https://github.com/reliaburger/reliaburger/blob/0eb6071da897b836d27e19d277a9a8e69a96ccbb/scripts/release/test_loop_summary.py#L43).

Fix the summary to distinguish pass/fail/skip/incomplete, compare actual evidence with expected lanes/tests/iterations, bind every record to candidate identity, and return non-zero for failed/incomplete qualification. Add subprocess tests of the exit status and mixed/missing/skipped inputs. A failed nextest step still fails its own GitHub job; this finding does **not** say that the summary overrides that failure or automatically permits release promotion. Label any statistical bound as conditional on independent repetitions of the tested scenario, not a production failure-rate guarantee.

**T04 — An interoperability test exists without a named automated owner.** The real `crane` TLS login/push/pull test is ignored; no `crane` provisioning/invocation was found in the checked CI/Makefile/release scripts. The manually excluded list in the harness document does not name it either. Give it a small provisioned standards-client job or an explicit release/manual owner. Then generate an inventory assigning every ignored test to a gate or an intentional deferred/manual category. `--no-tests=fail` only proves that a filter matched something. [tests/suite/registry_standard_clients.rs:348](https://github.com/reliaburger/reliaburger/blob/0eb6071da897b836d27e19d277a9a8e69a96ccbb/tests/suite/registry_standard_clients.rs#L348), [docs/design/test-harness.md:80](https://github.com/reliaburger/reliaburger/blob/0eb6071da897b836d27e19d277a9a8e69a96ccbb/docs/design/test-harness.md#L80), [Makefile:29](https://github.com/reliaburger/reliaburger/blob/0eb6071da897b836d27e19d277a9a8e69a96ccbb/Makefile#L29).

Do not flag every discarded result or snapshot as a weak test mechanically. For example, the Parquet overlong-integer tests explicitly promise only that opening hostile data returns without panicking; that assertion is intentionally different from requiring rejection. Assess the stated behaviour, not a count of `assert!` calls. [tests/suite/parquet_safety.rs:40](https://github.com/reliaburger/reliaburger/blob/0eb6071da897b836d27e19d277a9a8e69a96ccbb/tests/suite/parquet_safety.rs#L40).

## 4. Testing methods: what exists, what is missing, what to improve

The normal code-PR pipeline includes portable checks on Linux/macOS and, for PRs targeting main, heavier Linux/cluster/upgrade acceptance. Stacked PRs can skip heavy suites unless labelled `full-ci`; documentation-only changes skip Rust jobs except the files consumed by builds/tests. Main pushes and nightly runs select all source-CI groups. Release qualification and V02 loops are additional layers, not synonyms for a normal green PR. [scripts/ci/select-jobs.sh:1](https://github.com/reliaburger/reliaburger/blob/0eb6071da897b836d27e19d277a9a8e69a96ccbb/scripts/ci/select-jobs.sh#L1), [.github/workflows/ci.yml:3](https://github.com/reliaburger/reliaburger/blob/0eb6071da897b836d27e19d277a9a8e69a96ccbb/.github/workflows/ci.yml#L3).
