# Losing a node, run for real (Z6.7)

24 September 2026. Step 12 of the homepage tour stops one node of a
three-node laptop cluster and expects three frontends to run again within a
minute. While recording the tour it didn't, in two runs out of three. This is
the record of why, what changed, and the runs that show it now works.

## Setup

- Host: Apple M2 Max, 32 GiB, macOS 26.3.1. Lima 2.1.0 and the pinned Ubuntu
  guest image, as `relish setup --quickstart` installs them.
- Cluster: `relish setup --quickstart --development-binaries target/tour-bins`
  with an isolated `RELIABURGER_HOME`, default ports, nothing else running.
- Binaries: Linux aarch64 `bun` and `relish` built `--release --features ebpf`
  in the `reliaburger-test` Lima VM from `fix/node-loss` (the code of commit
  `6af5976`); the host `relish` a debug build of the same tree.
- Each run: `scripts/demo/tour.sh --setup target/tour-bins` (the whole tour,
  including the quickstart), then `relish local start node-3`, a wait for the
  cluster to settle, `relish status` and `relish wtf`, the three node journals,
  and `relish local destroy --yes`.

## Before: what the recording hit

A baseline run of the tour's base commit (`6dced0a`) reproduced it: after
`relish local stop node-3`, the frontend stayed at two running replicas for the
full five minutes the script watched.

```
rb-a7e4d9e026d3-1        default__frontend-0  frontend        default      stopped    -          0
rb-a7e4d9e026d3-1        default__frontend-g1-0 frontend        default      stopped    -          0
rb-a7e4d9e026d3-1        default__frontend-g1-1 frontend        default      running    4289       0
rb-a7e4d9e026d3-2        default__frontend-0  frontend        default      running    2489       0
```

Node-1 logged the same failure every thirty seconds:

```
04:46:57 orchestrator: deploy of frontend/default failed, will retry: old instance artifact
         retirement failed: cannot retire artifacts for default__frontend-0 yet: other nodes
         have not yet confirmed the endpoint's withdrawal; started replacements retained for cleanup
04:47:31 orchestrator: deploy of frontend/default failed, will retry: ... default__frontend-g1-0 ...
04:48:02 ... (the same, every 30 s until the run ended at 04:51:34)
```

Three things went wrong, and a fourth made it invisible.

1. **A stopped node blocked every address release.** Node-1 gains a replica
   by a rolling redeploy, which retires its old instance, and the leader
   confirms a release only when every registered consumer has confirmed the
   endpoint's withdrawal. Node-3 was registered and stopped, so the leader
   answered 202 for as long as it stayed down.
2. **A failed retirement churned replicas.** The rollout treated that 202 as
   failure. The orchestrator retried the deploy, which counted the two
   replacements it had already started as existing instances and, with three
   instances for a target of two, began by retiring one: `frontend-g1-0`, a
   healthy replica. Every later retry tried to retire it again. That's the
   two-of-three above. In the recording runs, with slightly different timing,
   the retries started new generations instead (g1 to g10).
3. **A new leader moved a survivor's replica.** In one recording run node-3
   was the leader, and the new leader moved node-2's untouched frontend to
   node-1. The leader's cluster cache treats a node without a readiness report
   as unready, and a new leader keeps only reports received in its own term;
   the three reports a node sends (state, capabilities, readiness) arrive as
   separate messages. The baseline run above had a different leader and didn't
   hit this, so the cause comes from the code and the recording's logs rather
   than a reproduction.
4. **`relish wtf` said nothing.** Its service check asks whether each service
   has a healthy backend. Two of three is still "a healthy backend".

## What changed

| Commit | Change |
|---|---|
| `ace2bab` | A consumer holds a 60 s view lease from each placement request whose answer it published. Wrapper, the agent loop and the kernel's connect hook (a new pinned `view_lease_map`) all stop routing when it lapses. The leader discharges a consumer it hasn't served for 80 s that gossip doesn't list as alive. |
| `213f696` | A rollout whose old instance is only waiting for remote confirmations hands it to the agent loop after 5 s and finishes. The deferred instance no longer counts as one of the app's instances. |
| `124c5eb` | A placement holds on a live node whose readiness or capability report hasn't arrived yet. |
| `57b3c67` | `wtf` warns `under-replicated` and names the nodes whose placements aren't running. |
| `6af5976` | The placement acceptance suite stops the leader node of three and checks all of the above on process nodes. |

The safety argument for discharging a silent node is in
`docs/design/discovery-onion.md` §7.6 and chapter 3 of the book ("When a node
goes quiet"). In short: the node's lease runs from before its request left and
lasts 60 s; the leader waits 80 s from after it served that request; both use
elapsed time, never wall clocks; serving and discharging a node take the same
lock; and the kernel enforces the lease even when Bun is dead.

Every run passed every wait in the tour. "Step 12" is the tour script's own
measurement, from `relish local stop node-3` returning (a graceful VM stop,
about 30 s) to three frontends running on the survivors.

| 2 | 112.1 s | 334 s | 27 s | 05:47:59 | 05:48:51 (+52 s) | by 05:48:56 | g1 only | 0 |
| 3 | 91.1 s | 298 s | 24 s | 05:54:09 | 05:55:04 (+55 s) | by 05:55:06 | g1 only | 0 |

In every run node-1 started two `g1` replacements, handed its old
`frontend-0` to the agent loop after the five-second patience, and finished
the rollout. The leader discharged node-3 once it had been silent past its lease,
and node-1 released the old replica within five seconds of that. Node-2's
frontend never moved. Step 12's `relish status`, from run 1:

```
rb-6e9c36ea8a22-1        default__frontend-0  frontend        default      stopped    -          1
rb-6e9c36ea8a22-1        default__frontend-g1-0 frontend        default      running    4296       0
```

`frontend-0` shows as `stopped` until its release completes, about a minute
later. The tour's `relish wtf` (step 13) reported one warning in every run, the
missing council member, and `[replicas] every app runs its desired replicas`.

**Node-3 coming back.** `relish local start node-3` took 9 to 10 s. The
cluster was steady at once in every run: three running frontends, nothing
else, for three consecutive polls; no new generation; `relish wtf` all OK
(12 checks). Node-3 took no frontend back: the survivors' placements held.

## A frozen node

Stopping a VM is the easy case: nothing on it routes. The hard case is a node
that is alive but silent. After recording the cast, on its cluster, node-2's
Bun was frozen with `SIGSTOP` (its containers and pinned eBPF programs kept
running) while a probe on node-2 itself connected to the frontend's virtual
address every five seconds:

```
06:18:19 freezing bun pid 2352 on rb-fd793c6996e0-2
06:19:15 +56s probe from node-2: 200 exit=0
06:19:20 +61s probe from node-2: 000 exit=7      <- the kernel refuses the VIP: lease lapsed
06:19:45 (node-1) scheduler: endpoint consumer rb-fd793c6996e0-2 silent past its view lease;
         its withdrawal receipts are no longer awaited
06:20:21 +122s probe from node-2: 000 exit=7
06:20:23 thawed
06:20:23 (node-2) bun: the leader hasn't answered for 60s; withdrawing the cluster view until it does
06:20:33 +10s after thaw, probe from node-2: 200 exit=0
```

The kernel stopped routing at 60 s with nobody to tell it to; the leader
discharged node-2 at 86 s; the leader had already moved node-2's frontend to
node-3, as it would for any node gossip calls dead. Thawed, node-2 withdrew its
view, registered again, republished and routed within ten seconds, and retired
its orphaned frontend two seconds later.

The same experiment first ran by mistake with node-3 still stopped from the
tour, so freezing node-2 cost the council its quorum. It shows the price of the
lease: after 60 s without a leader, node-1 also withdrew its view, `wtf`
reported every service without backends, and routing stopped until node-2
thawed. A council outage that long fails closed, by design.

`wtf` with a frontend missing (node-3 stopped again, `wtf` at once):

```
  [under-replicated] app frontend/default runs 2 of 3 replicas (app.frontend/default)
    1 replica placed on rb-fd793c6996e0-2 is not running
```

The leader had already placed the replacement on node-2, where it was still
starting.

## The recording

`docs/website/assets/tour.cast` was re-recorded afterwards with
`scripts/demo/tour.sh --record` against a fresh cluster (commit `8e3f22d`):
setup 92.7 s (played four times faster), step 12 three frontends 24 s after the
stop returned, 3 min 41 s of playback, 463 KB (16 KB gzipped).

## Still open

- A node whose agent can't reach a leader but whose gossip still answers is
  never discharged. Its releases wait for an operator, as before.
- A replica-count change is still a rolling redeploy on that node, so node-1
  restarts its existing frontend when it gains one.
