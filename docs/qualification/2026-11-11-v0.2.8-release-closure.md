# 0.2.8 release closure

10 to 12 November 2026. How the 0.2.8 candidates were qualified: what each
gate run found, and what fixed it. The per-run evidence lives in the records
this page links; this page is the map.

> **Candidate 3 (`e423d469`) is the release candidate.** It passed both
> staged installs, the power-cut and reboot lanes (25 of 25 in every lane),
> the V02 and jobs fast tiers and an extra V02 fast run on the seed that
> found #1849, all clean, with no agent-loop turn over budget. The 8-hour
> jobs final completed its whole schedule (8 cycles, four upgrade walks, and
> a quiet tail with every leak checker armed on every node) with no failure:
> "the release gate's final soak passes".
>
> Candidates 1 and 2 each failed a tier on a product bug, and both were
> replaced. Their records are kept as evidence:
> [candidate 1](2026-11-10-v0.2.8-candidate-1/README.md),
> [candidate 2](2026-11-11-v0.2.8-candidate-2/README.md).
>
> **Known issues it ships with:** none found by the gate.

## The gate

0.2.8 needs the full gate ([a gate scaled to the
release](../releasing.md#a-gate-scaled-to-the-release)). `release_tier.py`
found that it moves the wire format (protocol 57 to 58) and durable state
(state 73 to 74), and changes the agent loop (`src/bun/agent.rs` and 21
files under `src/bun/agent/`). `scripts/release/nightly.py freeze-check`
found no green nightly for the full gate, so every tier ran on each
candidate itself.

Each candidate's gate was two staged installs, the power-cut and reboot
lanes (25 runs each), the V02 fast tier, the jobs fast tier and the 8-hour
jobs final. From candidate 2 on, it also ran an extra V02 fast tier with
`--seed 3139726783`, which repeats candidate 1's deploy-kill then power-off
on one node. All of it ran on the Mac Studio, with nothing else built or
tested there while it ran.

## What the gate found

**The soak harness read the old status table.** 0.2.8's `relish status
-o json` became the cluster summary in the agent envelope
([#1788](https://github.com/reliaburger/reliaburger/pull/1788)), but
`qualify-sustained.sh` still read it as a list of instances. Candidate 1's
first V02 fast run failed in setup with all 11 apps running.
[#1850](https://github.com/reliaburger/reliaburger/pull/1850) reads
`relish apps --instances` instead. Every soak on this page ran with it.

**Bun crash-looped after a power cut ([#1849](https://github.com/reliaburger/reliaburger/issues/1849)).**
Candidate 1's V02 fast tier: a deploy-kill one second into a rollout, then a
power cut of the same node 90 seconds later, left an adoption record out of
step with its runtime generation, and every start after that exited ("adoption
log identity conflicts with runtime generation"). Fixed by
[#1851](https://github.com/reliaburger/reliaburger/pull/1851), which retires
such a generation, and [#1854](https://github.com/reliaburger/reliaburger/pull/1854),
which keys each adoption record write by its launch. The seeded runs on
candidates 2 and 3 repeated the sequence five times without a failure.

**A deploy_op turn waited for an fsync ([#1853](https://github.com/reliaburger/reliaburger/issues/1853)).**
Candidate 1's jobs fast tier: a 1,593 ms `finish_fresh_instance` turn during
the whole-cluster restart, waiting on the instance record's `fdatasync`.
[#1854](https://github.com/reliaburger/reliaburger/pull/1854) moves the
record and identity fsyncs off the loop.

**A missing-evidence 502 ([#1855](https://github.com/reliaburger/reliaburger/issues/1855)).**
Candidate 1's final: one ingress probe answered 502, five minutes after a
node came back from a power cut, then recovered.
[#1856](https://github.com/reliaburger/reliaburger/pull/1856) keeps a node's
backends when one inventory read misses its deadline.

**A blocking file call on the loop's thread ([#1857](https://github.com/reliaburger/reliaburger/issues/1857)).**
Candidate 2's seeded V02 run: a 1,152 ms `health_probe_result` turn, with
the thread running the agent loop in `lseek` on a busy disk.
[#1858](https://github.com/reliaburger/reliaburger/pull/1858) keeps blocking
file calls off the runtime's workers.

Candidate 2's final, stopped at 7 h 33 min when candidate 3 was staged, had
no failures; candidate 1's, stopped at 3 h 54 min, had only the 502.
