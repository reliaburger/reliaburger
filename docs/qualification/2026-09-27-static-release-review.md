## 1. Defects and concrete fixes

### B01 — P1: snapshot inputs can escape the authorised app's filesystem scope

**Evidence:** [src/bun/api.rs:4941](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/bun/api.rs#L4941), [src/bun/agent.rs:2141](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/bun/agent.rs#L2141), [src/grill/snapshot.rs:130](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/grill/snapshot.rs#L130), [src/grill/snapshot.rs:177](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/grill/snapshot.rs#L177), [src/grill/volume.rs:226](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/grill/volume.rs#L226).

The API checks the token against the route's namespace/app, then passes `volume` and `name` from JSON straight to the snapshot manager. The manager removes leading slashes from `volume` and joins the remainder under the app directory, without rejecting `..`. `backend_of` merely reads the sidecar at that resulting path. Thus a caller scoped to one app can select another app's existing Btrfs volume using a relative traversal. Separately, an absolute custom snapshot name replaces the destination root when joined; a name containing `..` can also escape it. The managed-volume creation path has traversal validation, but snapshot creation does not reuse it.

**Impact:** a scoped deployer can cause privileged snapshot operations outside the app they were authorised to manage. Exploitability depends on existing Btrfs volumes and destination layout; no claim of a reproduced arbitrary-file overwrite is made.

**Fix:** validate namespace/app and custom snapshot names as single components; resolve volume selection against the app's actual managed-volume inventory; reject parent components and symlink escapes at the filesystem boundary. Apply the same confinement to persisted metadata before restore/delete/upload.

**Regression:** through the real authenticated API, allow a normal snapshot and reject absolute names, parent paths, another namespace's volume, and symlink redirection before any filesystem mutation. Book: chapters 4–5.

### B02 — P1: multi-volume snapshots have ambiguous identities

**Evidence:** [src/bun/agent.rs:2135](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/bun/agent.rs#L2135), [src/grill/snapshot.rs:249](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/grill/snapshot.rs#L249), [src/grill/snapshot.rs:296](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/grill/snapshot.rs#L296), [src/grill/snapshot.rs:311](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/grill/snapshot.rs#L311), [src/bun/snapshot_worker.rs:126](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/bun/snapshot_worker.rs#L126).

Creating snapshots for all of an app's volumes deliberately gives them the same timestamp/name. `find(namespace, app, name)` returns the first matching metadata entry, ignoring volume. Restore therefore restores only one matching volume. Delete has the same ambiguity, and the retention sweep discards the volume identity when it calls delete by name.

**Failure example:** `/data` has an old snapshot named `100`, while `/wal` has its newest snapshot named `100`. Pruning the old `/data` snapshot can resolve to `/wal` and delete its retained backup instead. Equal timestamps retain filesystem enumeration order, which is not a stable identifier.

**Fix:** use a typed `(namespace, app, volume, snapshot_id)` identity internally and in deletion; define CLI/API semantics for a named multi-volume snapshot set. Refuse ambiguity rather than silently choosing one.

**Regression:** two volumes sharing timestamps/custom names; restore the requested volume or complete set; prune one volume without touching the other's retained backup. Book: chapter 5.

### B03 — P1: restore's stopped-app check does not protect the restore operation

**Evidence:** [src/bun/agent.rs:4273](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/bun/agent.rs#L4273), [src/grill/snapshot.rs:249](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/grill/snapshot.rs#L249). Existing test: [src/bun/agent.rs:14417](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/bun/agent.rs#L14417).

The agent checks that the app is stopped, then spawns a blocking restore and immediately resumes processing commands. There is no restore reservation in that branch. A deploy/reconcile command can start the app while restore is renaming its live volume; another restore can use the same `.restore-staged` and `.restore-old` paths concurrently. The existing test covers an app that is already running, not a start racing with an accepted restore.

**Fix:** reserve maintenance ownership before dispatching work, reject/defer deployment and competing volume operations until completion, and retain that ownership across caller cancellation. Do not simply move the blocking work back onto the agent loop.

**Regression:** pause restore after acceptance, attempt deployment and a second restore, then prove they cannot access/replace the live volume until the first operation resolves. Book: chapters 1 and 5.

### B04 — P1: snapshot restore is not crash-atomic

**Evidence:** [src/grill/snapshot.rs:265](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/grill/snapshot.rs#L265).

Restore removes previous staging/old directories, creates a staged copy, renames `live` to `.restore-old`, and then renames the staged copy to `live`. Individual renames are atomic; the sequence is not. A crash between them leaves no live volume. A retry unconditionally tries to delete `.restore-old`, potentially deleting the original data before the retry's rename of the missing `live` path fails. Failed rollback rename is also discarded. There is no durable transaction record resolving which copy owns the live name.

**Fix:** journal restore phases and reconcile them before workload adoption; preserve every candidate copy until recovery establishes the authoritative one. Make rollback/cleanup errors explicit. Use directory syncs and per-volume ownership rather than treating best-effort deletion as recovery.

**Regression:** actual owner death at each create/rename/checkpoint boundary on disposable Btrfs; restart must expose a complete old or restored volume and preserve ambiguous data for recovery. Book: chapters 5 and 15.

### B05 — P1: remote snapshot object names can overwrite another node's backup

**Evidence:** [src/bun/snapshot_worker.rs:40](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/bun/snapshot_worker.rs#L40), [src/bun/snapshot_worker.rs:197](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/bun/snapshot_worker.rs#L197), [src/grill/snapshot.rs:83](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/grill/snapshot.rs#L83).

An archive key contains only namespace, app, flattened volume path and snapshot name. It contains neither node/volume identity nor content digest, and upload uses an ordinary `put`. Two nodes using the same destination and taking same-second snapshots of a replicated app write the same key with different bytes. Custom-name reuse has the same problem. Independent nodes' local volumes are different data even when their app names match.

**Fix:** bind archives to stable node/volume identity and immutable snapshot identity (preferably a content digest), with explicit collision/conditional-write handling. Publish a manifest for discovery rather than overloading a human name as object identity.

**Regression:** two independent local stores, same app/path/time and shared destination; both archives survive with their original bytes. Also cover custom-name reuse. Book: chapter 5.

### B06 — P1: backup receipt does not identify the destination, and pruning runs before retrying uploads

**Evidence:** [src/grill/snapshot.rs:69](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/grill/snapshot.rs#L69), [src/bun/snapshot_worker.rs:126](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/bun/snapshot_worker.rs#L126), [src/bun/snapshot_worker.rs:142](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/bun/snapshot_worker.rs#L142), [src/bun/snapshot_worker.rs:210](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/bun/snapshot_worker.rs#L210).

`uploaded: bool` is the entire upload checkpoint. After uploading to destination A, changing `upload_url` to B leaves existing snapshots marked uploaded, so B receives none of them. Independently, the sweep prunes old snapshots before building the upload list, irrespective of `uploaded`. An outage longer than the retention window can delete snapshots that never made it off-node. With enabled scheduling and `retain = 0`, all newly created snapshots are pruned before upload; that combination is not refused by the snapshot config type.

**Fix:** receipt = destination identity + immutable archive identity + confirmed completion. Define the relationship between local retention, pending exports and disk-pressure limits explicitly; preserve unexported data or report an explicit policy-driven loss, rather than implying eventual retry. Validate zero retention when export is enabled. Reuse the principles already implemented for Ketchup's export acknowledgements.

**Regression:** destination change, repeated upload failure across more than `retain` ticks, recovery, and zero retention. Book: chapters 5–6.

### B07 — P2: large snapshot upload buffers the entire compressed archive in Bun's memory

**Evidence:** [src/bun/snapshot_worker.rs:177](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/bun/snapshot_worker.rs#L177).

`GzEncoder<Vec<u8>>` builds the complete tar.gz before `put`. `spawn_blocking` keeps compression off an async worker but does not bound its memory. A large, poorly compressible volume can consume gigabytes inside the node agent, undermining the backup and the orchestrator together. The upload tests use a tiny single-file fixture.

**Fix:** stream to a bounded multipart upload or a quota-controlled temporary spool; enforce archive/upload deadlines and cancellation ownership. Keep a retryable receipt until completion.

**Regression:** large incompressible fixture under a fixed memory budget, stalled destination, cancellation and disk-full spool. Book: chapters 5 and 15.

### B08 — P1: documented CPU/memory autoscaling does not consume the built-in collector's metrics

**Evidence:** [src/mayo/collector.rs:139](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/mayo/collector.rs#L139), [src/cluster/orchestrate.rs:680](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/cluster/orchestrate.rs#L680), [src/cluster/orchestrate.rs:730](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/cluster/orchestrate.rs#L730), [src/meat/autoscaler.rs:190](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/meat/autoscaler.rs#L190). Misleading acceptance coverage: [tests/placement.rs:656](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/tests/placement.rs#L656) and [tests/placement.rs:695](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/tests/placement.rs#L695).

The documented configuration uses `metric = "cpu"` or `"memory"`. The controller queries that exact metric name. The collector emits `process_cpu_percent` and `process_memory_bytes`; there is no alias/normalisation on this path. Normal built-in telemetry therefore produces no decision for `cpu`/`memory`. Selecting the raw collector names is not a correct workaround: the evaluator compares values against a fraction such as `0.70`, so percentages/bytes have the wrong units.

The live placement test injects a synthetic `cpu = 0.95` rollup into every node's store. It proves scaling from a suitable input, but bypasses the broken collector-to-controller contract. Custom scraped metrics already expressed as fractions are a distinct case.

**Fix:** define typed built-in resource metrics, collect actual workload resource usage, normalise against the documented CPU/memory budget and pass compatible units to the evaluator. Explicitly define custom metric units. Also define/reject scale-to-zero: `min = 0` is accepted while `compute_desired` returns immediately when current replicas are zero.

**Regression:** a real managed workload generates measured load; ordinary collection, rollup transport, leader evaluation and Raft override cause the expected scale change without injected store rows. Include memory, missing/stale samples, leader change and cooldown. Book: chapters 6 and 9.

### B09 — P2: Prometheus histogram and summary samples lose their meaning during ingestion

**Evidence:** [src/mayo/scrape.rs:16](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/mayo/scrape.rs#L16) and [src/mayo/scrape.rs:244](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/mayo/scrape.rs#L244). The locally installed source of the locked `prometheus-parse` 0.2.5 dependency was also inspected to confirm its bucket/quantile representation.

The conversion sums cumulative histogram bucket counts and emits one sample under the base name, dropping bucket bounds. For the existing fixture's buckets 10, 20 and 30, the base sample becomes 60; the original `_bucket{le=...}` series disappear. The separate `_sum` and `_count` samples do not repair that loss. Summary quantile values are likewise summed and lose their quantile labels. The test named `parse_histogram_extracts_count` only asserts that the result is non-empty.

**Fix:** preserve each histogram bucket with its `le` label and each summary quantile with its `quantile` label, plus sum/count. If the store cannot represent them, explicitly refuse/document them rather than presenting a fabricated scalar.

**Regression:** assert exact names, labels and values for the current histogram fixture and a summary fixture, then query them after flush/reopen. Book: chapter 6.

### B10 — P2: rate-limited GitOps deliveries become permanently rejected retries

**Evidence:** [src/lettuce/webhook.rs:94](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/lettuce/webhook.rs#L94) and [src/bun/api.rs:7654](https://github.com/reliaburger/reliaburger/blob/0a5dfc696a757193e4173af1618c64586c02f0b9/src/bun/api.rs#L7654).

Replay detection inserts the delivery ID before testing the rate limit. A valid new delivery exceeding the budget receives 429 but is already recorded as processed. Retrying it after the rate window returns the duplicate-delivery error (401), until eviction or restart. Poll-based sync may eventually fetch the commit, but the webhook retry contract remains broken.

**Fix:** check rate capacity before committing the replay ID, or commit replay/rate state only after admission. Preserve the API's existing queue-capacity reservation.

**Regression:** exhaust the budget, reject one signed delivery with 429, advance an injected clock past the window, accept the same ID exactly once, then reject a true replay. Book: chapter 7.

## 4. Recommended delivery order

1. **Triage B01–B06 and B08 before the tag.** They affect authorisation, existing user data/backups or a claimed built-in feature. For each, either fix with a failing-first regression or explicitly remove/refuse the affected release behaviour. No implementation was changed here.
2. **Repair test selection immediately alongside the first snapshot fix.** Make the Btrfs acceptance reachable and add the inventory check so future test renames cannot silently remove coverage.
3. **Fix B09 and B10, and bound B07.** Add the concrete assertion/retry/resource regressions; avoid expanding the feature scope while repairing current contracts.
4. **Finish V01–V04 in the existing release effort.** Add targeted reproductions to its queue after coordination; do not invalidate running soaks or restart their VMs merely to perform this review. Any source fix needs candidate-specific acceptance evidence before publication.
5. **Publish the concise 0.1.0 support contract.** Resolve the whitepaper contradictions, state backup/runtime/trust limits, and label performance figures as measured or target values. Link long-term F01–F12 separately.
6. **Update the book with each eventual fix.** Chapters 4–5: filesystem confinement, typed identities, crash consistency and maintenance ownership. Chapter 6: telemetry units and distribution fidelity. Chapter 7: transactional webhook admission. Chapters 14–15: exact compatibility, candidate identity and the difference between line coverage and behavioural evidence. Explain any new Rust types, ownership guards and async/blocking boundaries when first introduced.
7. **After 0.1.0, invest in confidence before breadth.** Prioritise independent-host fault campaigns, storage recovery and trusted boundary fuzzing; then deliver deferred capabilities in roadmap order. Keep optional module splitting separate from corrective patches.

A clean run of the present suite would not disprove the defects above: several sit precisely outside the suite's selected tests or behind synthetic inputs. The next useful step is narrowly targeted regression work on an independently provisioned environment, after the ongoing release work can accommodate it.
