# Competitive review: Reliaburger and thirteen alternatives

Reviewed 15 October 2026. This research writeup records competitive findings,
engineering recommendations and evidence limits. The public
[comparison pages](../website/compare/index.html) focus on choosing Reliaburger
and understanding the operational trade-offs.

## Evidence, versions and limits

This is a source and documentation review, not a comparative production trial. We inspected implementations where broad feature claims needed checking, read official installation and operations documentation, and checked release references on 15 October 2026. Linked code supports a narrowly stated observation; it does not establish that every execution reaches that path. We did not run the competing clusters, reproduce failure scenarios or measure their throughput. Commands on the individual pages are worked examples based on the cited interfaces, not a record of successful production deployments.

**Reliaburger has two baselines.** The public installer selects [0.1.6](https://github.com/reliaburger/reliaburger/releases/tag/v0.1.6). This review also examines the unreleased [0.2.1 train at `32effd96`](https://github.com/reliaburger/reliaburger/commit/32effd96e2a349d5a0533aa8a51c22b1054338d0). Train implementation is credited explicitly, but is not a released capability or proof of completed qualification. In particular, the train’s [rollout, retirement and cleanup behaviour](https://github.com/reliaburger/reliaburger/blob/32effd96e2a349d5a0533aa8a51c22b1054338d0/docs/README.md#stopping-and-retiring-workloads) must not be judged by older audit findings that it already addresses.

**Evidence labels used below:** “documented” describes an official contract; “source observation” describes the inspected revision; “judgement” is our interpretation for a specified workload. Negative findings mean “not provided by the inspected path or documented scope”, not “the project could never implement this”. A current documentation link may change; source links and release tags preserve the reviewed snapshot. Release recency, stars and implementation language are not reliability measurements.

## Which projects are better today?

There is no defensible universal winner without a workload, failure budget and operating team. There are clear winners for particular requirements. These judgements use capabilities and contracts, rather than an invented numerical score.

| Requirement | Better-supported choice today | Why; Reliaburger’s counterpoint |
|----|----|----|
| Kubernetes APIs, operators and portable storage integrations | Kubernetes or k3s | [Custom resources](https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/custom-resources/) and [persistent volumes / CSI](https://kubernetes.io/docs/concepts/storage/persistent-volumes/) are real extension contracts. Reliaburger offers [limited manifest conversion](https://github.com/reliaburger/reliaburger/blob/32effd96e2a349d5a0533aa8a51c22b1054338d0/docs/manual/09_kubernetes.md), not API compatibility. |
| A documented path for upgrading an existing long-lived cluster | Kubernetes, k3s or Nomad, within their compatibility rules | See [Kubernetes skew](https://kubernetes.io/releases/version-skew-policy/), [k3s upgrades](https://docs.k3s.io/upgrades) and [Nomad upgrades](https://developer.hashicorp.com/nomad/docs/upgrade). Reliaburger explicitly requires fresh clusters across pre-1.0 format changes; its same-format upgrade machinery is a narrower contract. [Policy](https://github.com/reliaburger/reliaburger/blob/32effd96e2a349d5a0533aa8a51c22b1054338d0/docs/releasing.md#compatibility-before-100). |
| Git-driven application hosting with previews and automated public HTTPS | Coolify or Dokploy | Their [preview environments](https://coolify.io/docs/applications/deployments/preview-deployments) and [domain workflow](https://docs.dokploy.com/docs/core/domains) are directly aimed at this job. Reliaburger’s [dashboard is read-only](https://github.com/reliaburger/reliaburger/blob/32effd96e2a349d5a0533aa8a51c22b1054338d0/docs/manual/04_observability.md#events-and-dashboards); its [TLS configuration](https://github.com/reliaburger/reliaburger/blob/32effd96e2a349d5a0533aa8a51c22b1054338d0/docs/manual/03_networking.md) is not an ACME onboarding workflow. |
| An existing Compose application on one reliable host | Docker Compose | [Production Compose](https://docs.docker.com/compose/how-tos/production/) preserves the existing service model. | A few Docker servers across networks or behind NAT | Uncloud, when its recovery limits are acceptable | Its [networking](https://uncloud.run/docs/#zero-config-overlay-network) combines WireGuard with connectivity management. This is an integration advantage, not measured superiority in availability or performance. |

## Reliaburger’s actual starting point

**Its strongest advantage is coherence.** The node agent integrates scheduling, membership, consensus, ingress, identity, image distribution, metrics, logs and fault injection. Operators can use the same app names in deployment and diagnosis. The source includes both an operations manual and explanations of the implementation. That reduces the number of separately selected components for this particular platform contract; it does not remove the need to understand quorum, certificates, storage and recovery. [Subsystems](https://github.com/reliaburger/reliaburger/tree/32effd96e2a349d5a0533aa8a51c22b1054338d0/docs/design), [manual](https://github.com/reliaburger/reliaburger/tree/32effd96e2a349d5a0533aa8a51c22b1054338d0/docs/manual), [book](https://github.com/reliaburger/reliaburger/tree/32effd96e2a349d5a0533aa8a51c22b1054338d0/docs/book).

**The operating envelope is narrower than the vision.** Container clusters use rootful Linux Runc with eBPF; rootless mode is standalone, and macOS containers run in managed Linux VMs. Local volumes do not become replicated storage simply because the control plane is replicated. Btrfs snapshots and object-storage backup are useful, but are not CSI or automatic volume relocation. These limits matter more than the number of configuration lines. [Runtime limits](https://github.com/reliaburger/reliaburger/blob/32effd96e2a349d5a0533aa8a51c22b1054338d0/docs/README.md#scope-and-limits), [volumes](https://github.com/reliaburger/reliaburger/blob/32effd96e2a349d5a0533aa8a51c22b1054338d0/docs/manual/11_images-and-volumes.md).

**Security claims must stay specific.** Digest-bound image admission, key-based upstream signature verification and role-separated trust are useful controls. They do not establish that Reliaburger is categorically “more secure” than Kubernetes, Docker or a PaaS. Configuration, patching, workload privileges and the recovery of signing material still matter. Keyless Sigstore support is a separate planned item, not a feature to credit here. [Image trust](https://github.com/reliaburger/reliaburger/blob/32effd96e2a349d5a0533aa8a51c22b1054338d0/docs/manual/10_security.md), [keyless plan](https://github.com/reliaburger/reliaburger/blob/32effd96e2a349d5a0533aa8a51c22b1054338d0/docs/plans/2026-10-05-plan-f03c-keyless-cosign.md).

**Upgrades are the largest adoption constraint.** The reviewed train uses protocol/state 52/69, while released 0.1.6 uses 46/63. Those are incompatible. The worker-first, council-member-at-a-time upgrade coordinator is meaningful engineering, but it does not provide a supported in-place migration from 0.1.6 into this train. Do not publish `relish upgrade start v0.2.1` as a working migration recipe. [Train compatibility](https://github.com/reliaburger/reliaburger/blob/32effd96e2a349d5a0533aa8a51c22b1054338d0/src/compatibility.rs), [released compatibility](https://github.com/reliaburger/reliaburger/blob/v0.1.6/src/compatibility.rs), [upgrade operations](https://github.com/reliaburger/reliaburger/blob/32effd96e2a349d5a0533aa8a51c22b1054338d0/docs/manual/12_operations.md#upgrading-bun).

## The platform alternatives

### Kubernetes and k3s

Kubernetes is the strongest choice here when applications depend on its API and extension ecosystem: controllers reconcile resources, operators add domain-specific behaviour, and storage integrations use established interfaces. Those are concrete capabilities, not a reason every small application needs Kubernetes. Its object model asks developers and operators to distinguish Pods, Deployments, Services, configuration, permissions and storage. [Workloads](https://kubernetes.io/docs/concepts/workloads/), [services](https://kubernetes.io/docs/concepts/services-networking/service/), [operators](https://kubernetes.io/docs/concepts/extend-kubernetes/operator/).

k3s is a particularly important comparison because it already addresses installation complexity. It bundles the container runtime, networking, DNS, ingress, service load balancing, network policy and local storage provisioning. Claiming that every Kubernetes user must assemble all of these independently would be misleading. k3s remains Kubernetes: a quick install does not replace the API concepts or make local-path storage survive loss of its host. [Included components](https://docs.k3s.io/), [networking](https://docs.k3s.io/networking/networking-services), [storage](https://docs.k3s.io/storage).

**Judgement:** Reliaburger’s narrower integrated workflow is an advantage when that workflow fits; Kubernetes and k3s provide the Kubernetes compatibility and extension contracts that Reliaburger does not. Adapt k3s’s explicit inventory of what is bundled and how each component is operated. Avoid competing on “single binary” alone. The dedicated [Kubernetes](../website/compare/kubernetes.html) and [k3s](../website/compare/k3s.html) pages compare installation, concepts, commands and upgrades.

### Nomad

Nomad’s job/group/task/allocation model is a useful contrast to an app-centred API. Co-scheduled task groups, task drivers and CSI provide scope Reliaburger should not dismiss as unnecessary ceremony. Native service discovery exists; Consul is optional for that path, not an unconditional requirement for every Nomad installation. [Job specification](https://developer.hashicorp.com/nomad/docs/job-specification), [task drivers](https://developer.hashicorp.com/nomad/docs/drivers), [native discovery](https://developer.hashicorp.com/nomad/docs/job-declare/service-discovery), [storage](https://developer.hashicorp.com/nomad/docs/stateful-workloads).

Nomad wins when the workload model and external integrations are the requirement. Reliaburger’s counterpoint is owning ingress, registry, logs, metrics and diagnostic commands as one platform. Adapt Nomad’s plan-before-run workflow and explicit deployment status, while preserving Reliaburger’s concise app model. A plan is evidence of intended changes, not a guarantee about capacity at a future time. [Plan command](https://developer.hashicorp.com/nomad/commands/job/plan), [detailed comparison](../website/compare/nomad.html).

### Uncloud

Uncloud is a close alternative for small Docker clusters: Compose input, a WireGuard network, Caddy ingress and automatic certificates solve practical deployment problems. It uses a decentralised state model rather than a Raft control-plane quorum. This makes different trade-offs, not an automatic availability victory. The Compose support matrix is deliberately a subset. [Tagged overview](https://github.com/psviderski/uncloud/blob/v0.21.0/README.md), [supported Compose fields](https://github.com/psviderski/uncloud/blob/v0.21.0/website/docs/8-compose-file-reference/1-support-matrix.md).

Uncloud’s documented rolling deployment can roll back a failed container replacement; previously updated containers stay on their new version. It is not an atomic whole-service rollback. Its published scope does not include automatically rescheduling a service when a machine disappears. Reliaburger’s desired-state scheduler is therefore relevant, while Uncloud has the stronger ready-made cross-network and public HTTPS story. [Rolling deployments](https://github.com/psviderski/uncloud/blob/v0.21.0/website/docs/4-guides/1-deployments/4-rolling-deployments.md), [scope](https://uncloud.run/), [detailed comparison](../website/compare/uncloud.html).

### Docker Compose, Docker Swarm and Kamal

Compose is a legitimate production option for one Docker host. Its services, networks, volumes and override files are often all a small deployment needs. It does not turn several hosts into a scheduler with automatic replacement elsewhere after host failure. Reliaburger becomes interesting at that boundary, provided the workload’s data can also recover. [Production Compose](https://docs.docker.com/compose/how-tos/production/), [Compose application model](https://docs.docker.com/compose/intro/compose-application-model/), [detailed comparison](../website/compare/docker-compose.html).

Swarm adds manager consensus, desired-state services, overlay networking, mutual TLS and rolling service updates to Docker Engine. It deserves a trial against Reliaburger for a Docker-native cluster; describing it as “dead” is not a technical comparison. Swarm does not by itself supply the application preview, Git build and database restore workflow of a PaaS. Adapt its join/deploy ergonomics and the clear separation between a Compose application and a Swarm service. [Swarm mode](https://docs.docker.com/engine/swarm/), [services](https://docs.docker.com/engine/swarm/services/), [networking](https://docs.docker.com/engine/swarm/networking/).

Kamal is an adjacent deployment tool rather than a continuously reconciling cluster scheduler. It builds and ships containers over SSH, with a proxy handling the traffic switch. Its appeal is the small operational surface for teams that already know their servers. Multi-host traffic and certificates need careful reading: the proxy documentation distinguishes single-server automatic TLS from multi-server arrangements. Adapt its visible deployment stages and concise rollback workflow. [Kamal deployment](https://kamal-deploy.org/docs/), [proxy configuration](https://kamal-deploy.org/docs/configuration/proxy/), [commands](https://kamal-deploy.org/docs/commands/deploy/).

## The application platforms

### Coolify

Coolify is ahead for an application team asking for a UI, Git-connected builds, provider preview deployments, domains and database backups. Those are complete user tasks, not just a list of components. Reliaburger’s read-only dashboard does not offer an equivalent deployment workflow. The fair comparison is developer experience versus the integrated scheduler and diagnosis model. [Preview deployments](https://coolify.io/docs/applications/deployments/preview-deployments), [databases](https://coolify.io/docs/databases/), [detailed comparison](../website/compare/coolify.html).

Its multi-server support must not be presented as automatic cluster HA: the current documentation requires an external load balancer, and the inspected application model refuses the additional-server path for Compose applications and applications with persistent storage. Existing containers continuing when the control UI is unavailable is different from placing replacements after a server dies. Coolify also documents storage-mount backups; older comparisons that say it only backs up databases should be updated. [Scaling overview](https://coolify.io/docs/core/infrastructure/scaling/overview), [eligibility checks](https://github.com/coollabsio/coolify/blob/f55efc859dfcbbf79274c4907b3df89f9767c11d/app/Models/Application.php#L606), [backup documentation](https://coolify.io/docs/core/persistent-storage/storage-mounts/backups).

### Dokploy

Dokploy is another serious PaaS comparator. Build choices, templates, Git-triggered previews, Traefik domains and database/volume backups are useful ideas for reducing the path from repository to running service. It distinguishes Docker Compose deployment from Docker Stack deployment on Swarm; remote deployment alone is not evidence of a distributed scheduler. [Build types](https://docs.dokploy.com/docs/core/applications/build-type), [previews](https://docs.dokploy.com/docs/core/applications/preview-deployments), [deployment options](https://docs.dokploy.com/docs/core/deployment-options), [Compose](https://docs.dokploy.com/docs/core/docker-compose).

The documented installation includes a dashboard, PostgreSQL and Traefik. A Swarm-backed workload does not make the dashboard database or its local files automatically highly available. Database-engine dumps and named-volume backups also have different consistency contracts; a restore exercise must test the one the application actually uses. This is a reason to define failure domains, not to dismiss the product. [Architecture](https://docs.dokploy.com/docs/core/architecture), [manual installation](https://docs.dokploy.com/docs/core/manual-installation), [database backups](https://docs.dokploy.com/docs/core/databases/backups), [volume backups](https://docs.dokploy.com/docs/core/volume-backups).

**Judgement:** Coolify and Dokploy are better fits today for self-service web application hosting. Reliaburger is a better candidate when the important requirement is a programmable cluster with integrated diagnostic and fault-testing tools. Adapt a small, honest deployment UI and a complete preview lifecycle, rather than trying to reproduce every PaaS integration at once. The boundary should stay visible: who builds, who schedules, who stores secrets, and who restores the database.

## The smaller projects: useful ideas, uneven evidence

### Orca

Orca is unusually close in presentation: Rust, TOML, an integrated proxy and both container and Wasm workloads. There is real code worth studying for ACME startup, Compose import and backup hooks. These are implementation observations at the inspected development revision, not a claim about every stable release. [Server and TLS setup](https://github.com/mighty840/orca/blob/b9146c2f0e9e99fcb924c5807b92c76043efdafe/crates/orca-cli/src/handlers/server.rs), [Compose importer](https://github.com/mighty840/orca/blob/b9146c2f0e9e99fcb924c5807b92c76043efdafe/crates/orca-core/src/import/compose.rs), [backup runner](https://github.com/mighty840/orca/blob/b9146c2f0e9e99fcb924c5807b92c76043efdafe/crates/orca-cli/src/handlers/volume_backup/run.rs).

The cluster claim needs qualification. The inspected server starts with local redb storage and mounts the ordinary API; finding Raft-related modules in the repository does not show a live replicated control plane. The actual placement function selects an explicitly pinned registered node, or returns local placement when there is no pin. That is different from automatic resource-aware placement across a cluster. [Server construction](https://github.com/mighty840/orca/blob/b9146c2f0e9e99fcb924c5807b92c76043efdafe/crates/orca-control/src/lib.rs#L105), [API construction](https://github.com/mighty840/orca/blob/b9146c2f0e9e99fcb924c5807b92c76043efdafe/crates/orca-control/src/api/mod.rs#L84), [placement](https://github.com/mighty840/orca/blob/b9146c2f0e9e99fcb924c5807b92c76043efdafe/crates/orca-control/src/placement.rs#L129).

Its Wasm implementation is an interesting experiment, but the inspected runtime’s HTTP entry-point assumptions should not be equated with arbitrary container compatibility or a complete WASI HTTP platform. **Judgement:** study Orca’s small application workflow, ACME and backup hooks; do not rank its HA above Reliaburger on the basis of module names or README claims. [Wasm runtime](https://github.com/mighty840/orca/blob/b9146c2f0e9e99fcb924c5807b92c76043efdafe/crates/orca-agent/src/wasm/runtime.rs).

### Gubernator

Gubernator has a broad interface and useful integration ideas: Compose stacks, an LDAP authentication path, deployment of familiar monitoring components and Sloth-based SLO definitions. These demonstrate an attempt to package common operations for users. [Stack API](https://github.com/mario-ezquerro/gubernator/blob/3724d45a2ddcb80e6d7f35a216b0da7fe0b34da6/internal/api/stack.go), [LDAP](https://github.com/mario-ezquerro/gubernator/blob/3724d45a2ddcb80e6d7f35a216b0da7fe0b34da6/internal/auth/ldap.go), [monitoring deployment](https://github.com/mario-ezquerro/gubernator/blob/3724d45a2ddcb80e6d7f35a216b0da7fe0b34da6/internal/monitor/deploy.go), [SLO implementation](https://github.com/mario-ezquerro/gubernator/blob/3724d45a2ddcb80e6d7f35a216b0da7fe0b34da6/internal/slo/slo.go).

Two inspected paths prevent treating its dashboard as evidence of equivalent telemetry or image security. The normal eBPF engine loop periodically generates flows between randomly selected discovered endpoints, with generated latency, byte counts and errors; the simulation flag increases the density rather than gating generation. The image-verification function returns “verified” from stored status or selected image-name prefixes once trusted keys exist, without cryptographically verifying that image’s digest in that function. These are precise source observations, not a reproduced exploit or a claim that every displayed metric is synthetic. [Flow generation](https://github.com/mario-ezquerro/gubernator/blob/3724d45a2ddcb80e6d7f35a216b0da7fe0b34da6/internal/ebpf/engine.go#L73), [signature decision](https://github.com/mario-ezquerro/gubernator/blob/3724d45a2ddcb80e6d7f35a216b0da7fe0b34da6/internal/security/signing.go#L128).

The repository’s HA proposal is a design document, not proof that the current SQLite manager is a replicated consensus service. **Judgement:** borrow the presentation of operational tasks and standards integrations, but independently validate advertised guarantees before recommending it as a production replacement. In particular, Reliaburger should preserve the distinction between measured, inferred and simulated telemetry in every UI. [HA specification](https://github.com/mario-ezquerro/gubernator/blob/3724d45a2ddcb80e6d7f35a216b0da7fe0b34da6/SPEC-ha.md), [architecture](https://github.com/mario-ezquerro/gubernator/blob/3724d45a2ddcb80e6d7f35a216b0da7fe0b34da6/architecture.md).

### Orbit

Orbit is best understood as a local Docker controller with an integrated Pingora proxy and scaling experiments. The inspected Docker runtime connects to the local daemon. This is a materially different scope from a distributed cluster control plane. Its resource and response-time feedback is interesting for ingress-aware scaling research. [Docker connection](https://github.com/AirPipeIO/orbit/blob/d8be9fd9f9f3f49c0620e4816f1429fc947598ed/src/container/runtimes/docker.rs#L35), [proxy](https://github.com/AirPipeIO/orbit/blob/d8be9fd9f9f3f49c0620e4816f1429fc947598ed/src/proxy.rs), [scaling code](https://github.com/AirPipeIO/orbit/tree/d8be9fd9f9f3f49c0620e4816f1429fc947598ed/src/container/scaling).

Operational details deserve testing before adoption: orphan adoption defaults to false, so startup behaviour is not automatically equivalent to preserving all previously managed instances. The status/metrics listener binds to all interfaces without an authentication layer in the inspected startup path. That is an exposed observability endpoint, not evidence of an unauthenticated deployment API. Its CoDel-inspired feedback uses response timing; calling this measured request-queue delay would overstate the implementation. [Configuration defaults and startup cleanup](https://github.com/AirPipeIO/orbit/blob/d8be9fd9f9f3f49c0620e4816f1429fc947598ed/src/config/mod.rs), [listener startup](https://github.com/AirPipeIO/orbit/blob/d8be9fd9f9f3f49c0620e4816f1429fc947598ed/src/main.rs#L156), [response-time input](https://github.com/AirPipeIO/orbit/blob/d8be9fd9f9f3f49c0620e4816f1429fc947598ed/src/proxy.rs#L75), [controller](https://github.com/AirPipeIO/orbit/blob/d8be9fd9f9f3f49c0620e4816f1429fc947598ed/src/container/scaling/codel.rs).

**Judgement:** it is an adjacent autoscaling experiment, not an objectively stronger cluster platform. Adapt the question it asks: can observed ingress delay guide scaling better than CPU alone? Answer it with measured queue time, saturation tests and explicit stability criteria before shipping a new controller.

### Simplecontainer / SMR

SMR is a real orchestration effort with etcd/raft, Docker workloads, networking and declarative resource kinds. Its architecture uses both a Raft replication layer and local etcd-backed object state; it should not be reduced to “a Docker wrapper”. OCI-distributed packs, dependency/init states and GitOps provide concrete ideas for a small-platform user experience. [Architecture and resource model](https://github.com/simplecontainer/smr/blob/789137f65c363a1da3eaa78c56bf0fa0a52aaae4/README.md), [Raft](https://github.com/simplecontainer/smr/blob/789137f65c363a1da3eaa78c56bf0fa0a52aaae4/pkg/raft/Raft.go), [packs](https://github.com/simplecontainer/smr/blob/789137f65c363a1da3eaa78c56bf0fa0a52aaae4/pkg/packer/OCI.go).

The implementation suggests specific qualification work. Placement is based on explicit/default nodes and replica distribution, rather than a demonstrated CPU-aware autoscheduler. Snapshot recovery references values in local etcd, so a clean-machine restore needs testing beyond replaying a Raft log. In the inspected Ready-processing loop, return values from snapshot/WAL persistence are not checked before subsequent state/message handling. That is a durability concern to investigate with injected I/O errors, not a claim that we reproduced data loss. [Placement](https://github.com/simplecontainer/smr/blob/789137f65c363a1da3eaa78c56bf0fa0a52aaae4/pkg/kinds/containers/platforms/replicas/Replicas.go), [snapshot state](https://github.com/simplecontainer/smr/blob/789137f65c363a1da3eaa78c56bf0fa0a52aaae4/pkg/raft/KVStore.go#L132), [persistence handling](https://github.com/simplecontainer/smr/blob/789137f65c363a1da3eaa78c56bf0fa0a52aaae4/pkg/raft/Raft.go#L637).

**Judgement:** worth studying, particularly packs and transparent dependency states; there is not enough evidence here to rank its recovery guarantees above Reliaburger’s. Its GitOps code can commit and push changes, a useful convenience with an authority trade-off: prefer a reviewable change proposal to an invisible second writer of desired state. [GitOps commit](https://github.com/simplecontainer/smr/blob/789137f65c363a1da3eaa78c56bf0fa0a52aaae4/pkg/kinds/gitops/implementation/Commit.go), [Git operations](https://github.com/simplecontainer/smr/blob/789137f65c363a1da3eaa78c56bf0fa0a52aaae4/pkg/kinds/gitops/implementation/internal/Git.go).

## Compare operations, not just installation lines

The six detailed pages use ordinary web-service tasks: deploy, inspect, read logs, change replicas, update an application and upgrade the platform. Examples state what must already exist. A laptop quickstart, a single-node server and a redundant production cluster are different installations. An HTTPS endpoint also needs DNS, reachable ports and certificate ownership; a replicated stateless service is not a replicated database.

| Approach | Concepts you need first | Installation and upgrade lesson |
|----|----|----|
| [Reliaburger / Kubernetes](../website/compare/kubernetes.html#concepts) | App and replicas versus Deployment, Pod and Service; both still need node, network, identity and storage knowledge. | Compare the full kubeadm setup with a full Linux cluster, not just `kubeadm init` with a laptop installer. Separate manifest conversion from API compatibility. |
| [Reliaburger / k3s](../website/compare/k3s.html#concepts) | Same Kubernetes workload model; fewer initial component choices. | Bundling helps installation. HA topology, datastore backup and orderly upgrades still need an operator. |
| [Reliaburger / Nomad](../website/compare/nomad.html#concepts) | App versus job, task group, task and allocation. | Read the proposed job change before applying it. Distinguish application rollout from server/client upgrade. |
| [Reliaburger / Coolify](../website/compare/coolify.html#concepts) | Application, project, environment and target server. | UI setup reduces command memorisation. The operator still owns SSH access, persistent data, control-plane backups and upgrades. |
| [Reliaburger / Uncloud](../website/compare/uncloud.html#concepts) | Compose service, machine, published endpoint and private mesh. | The installer is easy to read; recovery after machine loss and partial rollout still need explicit decisions. |
| [Reliaburger / Compose](../website/compare/docker-compose.html#concepts) | Project, service, network and volume on one Docker engine. | Updating a service, updating the Compose plugin and updating Docker Engine are separate operations. |

These are qualitative learning-curve judgements based on the linked workflows. We have not measured onboarding time. A team already fluent in Kubernetes may find a new TOML model harder to adopt than k3s. A developer shipping one app may get further with Coolify than with either cluster API. “Fewer concepts for this task” is defensible; “learn it in ten minutes” needs a user study.

Backup and upgrade evaluation should include the same acceptance criteria for every candidate: restore to clean machines, recover credentials, confirm application data, rehearse a failed upgrade and preserve an auditable record. A tar archive, a database dump, a control-plane snapshot and a running-volume snapshot are different artefacts. The linked [Reliaburger volume](https://github.com/reliaburger/reliaburger/blob/32effd96e2a349d5a0533aa8a51c22b1054338d0/docs/manual/11_images-and-volumes.md), [k3s backup](https://docs.k3s.io/cli/etcd-snapshot), [Nomad snapshot](https://developer.hashicorp.com/nomad/commands/operator/snapshot/save) and [Dokploy platform backup](https://docs.dokploy.com/docs/core/backups) interfaces illustrate why a single “backups: yes” cell would be misleading.

## What Reliaburger should adapt

The following is a prioritised recommendation, not a committed roadmap. Priority reflects how directly an idea removes an adoption obstacle while preserving the existing operating model. The evidence above motivates each proposal; the acceptance criteria are proposed work.

1.  **Prove the safety and recovery contract before expanding the surface.** Finish the train’s qualification, publish its limits, and add clean-machine restore exercises with clear failure outcomes. Document what future compatibility would promise without claiming it exists now. This addresses the [pre-1.0 upgrade constraint](https://github.com/reliaburger/reliaburger/blob/32effd96e2a349d5a0533aa8a51c22b1054338d0/docs/releasing.md#compatibility-before-100) and follows the explicit upgrade contracts in [Kubernetes](https://kubernetes.io/releases/version-skew-policy/) and [Nomad](https://developer.hashicorp.com/nomad/docs/upgrade). Acceptance: a second operator can rebuild from the documented artefacts and verify workload data, not merely start the API.

2.  **Add an end-to-end public HTTPS path.** Borrow from [Uncloud/Caddy](../website/compare/uncloud.html) and [Dokploy domains](https://docs.dokploy.com/docs/core/domains): DNS preflight, ACME issuance, renewal, storage, failover and useful errors. Acceptance: lose the issuing node and still serve a valid certificate; test rate limits and renewal failures. This is a more immediate web-hosting improvement than another runtime.

3.  **Make backup and restore an application workflow.** Borrow application-aware hooks and engine-specific dumps from [Orca](https://github.com/mighty840/orca/blob/b9146c2f0e9e99fcb924c5807b92c76043efdafe/crates/orca-cli/src/handlers/volume_backup/run.rs) and [Dokploy](https://docs.dokploy.com/docs/core/databases/backups). Distinguish crash-consistent snapshots, application-consistent backups, credentials and control-plane state. Acceptance: restoration checks data and identity on a clean host, including interrupted backups and missing keys.

4.  **Offer a strict Compose adoption path and small reusable packages.** Learn from [Uncloud’s field matrix](https://github.com/psviderski/uncloud/blob/v0.21.0/website/docs/8-compose-file-reference/1-support-matrix.md) and [SMR packs](https://github.com/simplecontainer/smr/blob/789137f65c363a1da3eaa78c56bf0fa0a52aaae4/pkg/packer/OCI.go). Conversion should report every unsupported semantic, especially networks, dependencies, mounts and restart policy. Acceptance: reject or explain loss before applying anything; packages have pinned images, versioned inputs and reviewable output.

5.  **Make the proposed change and its outcome visible.** Adapt [Nomad plans](https://developer.hashicorp.com/nomad/commands/job/plan) and the task-focused PaaS workflow. Show affected replicas, unavailable capacity, data placement and the exact reason progress stops. Add a modest deployment UI before a general platform console. Acceptance: CLI and UI show the same authoritative state; uncertain actions remain explicitly unknown.

6.  **Add preview environments only with their complete lifecycle.** [Coolify](https://coolify.io/docs/applications/deployments/preview-deployments) and [Dokploy](https://docs.dokploy.com/docs/core/applications/preview-deployments) make the demand clear. A useful implementation needs isolated credentials, DNS, quotas, data policy, untrusted-fork handling and cleanup after merge or expiry. Acceptance: previews cannot inherit production secrets implicitly, and abandoned environments stop consuming resources.

7.  **Evaluate optional connectivity and standards integrations against actual users.** [Uncloud’s mesh](../website/compare/uncloud.html) addresses a real direct-connectivity constraint; [Gubernator’s monitoring packaging](https://github.com/mario-ezquerro/gubernator/blob/3724d45a2ddcb80e6d7f35a216b0da7fe0b34da6/internal/monitor/deploy.go) shows the appeal of familiar tools. Prototype an explicit mesh option and reliable telemetry export before replacing the internal model. Acceptance: users can trace one incident across the boundary without duplicate or synthetic measurements being presented as observed facts.

Two existing features are foundations for this work, not missing capabilities: `relish compile config/ > all.toml` already resolves defaults and derived namespaces, and `relish apply --dry-run` already previews desired-spec changes. Extend those with explicit image-digest locking, provenance and scheduling-aware consequences rather than introducing a parallel planning model. Nomad's canary promotion and modify-index protection are useful references for that extension. [Configuration compilation](https://github.com/reliaburger/reliaburger/blob/32effd96e2a349d5a0533aa8a51c22b1054338d0/docs/manual/01_deploy-an-app.md#many-files), [current planner](https://github.com/reliaburger/reliaburger/blob/32effd96e2a349d5a0533aa8a51c22b1054338d0/src/relish/plan.rs), [Nomad plans](https://developer.hashicorp.com/nomad/commands/job/plan), [Nomad update policy](https://developer.hashicorp.com/nomad/docs/job-specification/update).

AI assistants, broad Wasm support and more dashboard panels are lower priorities in this judgement. The review does not establish that they remove the current blockers of recovery, upgrade compatibility, public HTTPS or application-data management.

## What a scientific comparison would measure next

A reproducible trial should publish exact versions, operating systems, machine specifications, image digests, manifests, scripts and raw results. Use equivalent redundancy and application semantics. Test stateless HTTP separately from a stateful service; pin the storage and ingress choices so a bundled local disk is not compared with a separately replicated volume as though they were equivalent.

Run repeated clean installations and measure operator actions and errors, not just shell-command count. Exercise an application update with a bad health check, worker loss, control-plane member loss, a partition, disk exhaustion, certificate renewal, a failed platform upgrade and restore to new hosts. Measure request failures, recovery time, lost or duplicated application writes, resource use and manual interventions. Define acceptable outcomes before running the tests, including cases where refusing an unsafe action is the correct result.

Recruit users with different prior experience for a learning study: new container users, Compose users and existing Kubernetes/Nomad operators. Give each the same tasks and record completion, mistakes and required help. Publish distributions and uncertainty instead of one headline time. Until those experiments exist, this review supports architectural and workflow choices; it cannot establish a universal speed, reliability or security ranking.
